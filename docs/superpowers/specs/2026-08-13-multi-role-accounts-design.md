# 多角色账号设计

日期：2026-08-13

## 目标

让同一账号同时拥有系统管理员、教师、家长和学生角色，并允许用户在登录时选择已授权角色、登录后切换角色。角色切换不能覆盖其他角色，也不能影响其他设备上的会话。

本设计同时修复两个现有问题：

1. 已是机构管理员的账号再次添加为教师时，接口提示成功但角色没有保存。
2. 登录接口会把前端选择的角色直接写入 `UserAccount.role_type`，普通账号可能借此提升为管理员。

## 当前根因

- `UserAccount.role_type` 只能保存一个全局角色。
- `InstitutionMember` 对 `(institution, user)` 设置唯一约束，因此一个账号在同一机构只能保存一个机构角色。
- `AddMemberSerializer` 使用 `get_or_create(institution, user)`。已有且仍为 active 的成员不会更新 `role`，但接口仍返回成功。
- `get_or_create_user()` 在每次登录时将请求中的 `role_type` 写回用户表，角色选择被错误地当成角色授权。
- 权限代码普遍直接读取持久化的 `request.user.role_type`，无法表达一个账号的多个并发角色会话。

## 方案选择

采用“独立角色授权表 + JWT 当前角色”。不采用 JSON 角色数组，因为其唯一性、查询和审计能力较弱；不完全依赖业务关系实时推导角色，因为系统管理员等全局角色无法统一表达，登录前角色判断也会复杂化。

## 数据模型

### UserRole

新增 `UserRole`：

- `user`：关联 `UserAccount`
- `role`：`admin`、`teacher`、`parent`、`student`
- `status`：`active`、`inactive`
- `granted_at`
- `updated_at`
- 唯一约束：`(user, role)`

`UserAccount.role_type` 在迁移期保留，作为旧数据的默认角色和旧代码兼容字段，但不再代表账号唯一授权，也不再因登录或切换角色而写入。

为 `UserAccount` 提供集中式角色能力：

- `get_roles()`：返回有效角色集合。
- `has_role(role)`：判断账号是否拥有有效角色。
- `grant_role(role)`：幂等授予或恢复角色。
- `revoke_role(role)`：停用角色，不删除审计记录。

### InstitutionMember

机构角色仅包含：

- `admin`：机构管理员，不等于系统管理员。
- `teacher`：机构教师。

将唯一约束调整为 `(institution, user, role)`，从而允许一个账号在同一机构同时拥有管理员和教师角色。保留每个角色自己的 `status`，以便分别停用和恢复。

列表接口按用户聚合机构关系，返回一张成员记录及 `roles` 集合；底层查询仍可用 `role='admin'` 或 `role='teacher'`，减少对现有机构和班级权限代码的影响。

## 数据迁移

数据迁移必须可重复且不破坏现有账号：

1. 将每个用户当前 `UserAccount.role_type` 写入一条 active `UserRole`。
2. active 的机构教师关系补充 `teacher`。
3. active 的班级学生关系补充 `student`。
4. active 的家长绑定关系补充 `parent`。
5. 现有机构管理员关系只保留为机构级 `admin`，不会单独提升全局系统管理员；已有 `UserAccount.role_type='admin'` 的账号因步骤 1 保留系统管理员角色。
6. 保留 `UserAccount.role_type` 原值，确保迁移过程可回滚并兼容旧令牌。

## 角色授予规则

- 系统管理员：只能通过系统级管理操作或初始化管理命令授予。
- 教师：在机构成员管理中添加教师关系时自动授予。
- 学生：成功加入班级或管理员将其加入班级时自动授予。
- 家长：完成有效的学生家长绑定时自动授予。
- 机构管理员：只授予机构范围内的管理权限，不自动授予系统管理员。

业务关系的删除或停用不会在第一版自动撤销全局角色，因为账号可能在其他机构、班级或绑定关系中仍需要该角色。显式撤销全局角色必须由系统级管理操作执行。

## 登录与令牌

登录页保留管理员、教师、家长、学生四个选项。

登录流程：

1. 验证手机号和验证码。
2. 查找账号，不再根据请求角色修改用户表。
3. 验证所选角色属于账号的 active `UserRole`。
4. 未授权时返回稳定错误码 `ROLE_NOT_GRANTED` 和用户可读提示“该账号未开通此角色”。
5. 授权通过后，为 refresh/access token 写入 `active_role`。
6. 登录响应返回 `roles`、`active_role`，并为兼容现有前端令 `role_type` 等于本次会话角色。

旧令牌没有 `active_role` 时，短期回退到用户原 `role_type`；新登录和新刷新令牌始终携带 `active_role`。

刷新访问令牌时必须保留 `active_role`。退出登录仍由客户端清理令牌。

## 角色切换

新增受认证接口 `POST /api/v1/auth/switch-role`：

```json
{
  "role": "teacher"
}
```

接口验证账号仍拥有目标角色，成功后签发一组新的 access/refresh token，并返回更新后的用户会话视图。它不更新 `UserAccount.role_type`，因此不同浏览器或设备可以同时使用不同角色。

管理员、教师、学生和家长的公共导航区域增加“切换身份”入口，只显示 `roles` 中有效的角色。切换后使用 `active_role` 跳转到对应首页：

- `admin`：管理员首页
- `teacher`：教师工作台
- `student`：学生首页
- `parent`：家长/学生端容器中的家长视图

## 请求认证与权限

自定义 JWT 认证在验证令牌后：

1. 读取 `active_role`，旧令牌则读取兼容角色。
2. 再次确认账号仍拥有该角色，防止角色撤销后旧令牌继续使用。
3. 将当前会话角色放入请求上下文。

所有敏感权限判断必须使用集中式请求角色方法，不再把数据库中的 `UserAccount.role_type` 当作当前会话：

- 系统管理：active role 为 `admin` 且账号拥有 `admin`。
- 教师操作：active role 为 `teacher`，并满足机构教师或班级教师关系。
- 学生操作：active role 为 `student`，并满足班级学生关系。
- 家长操作：active role 为 `parent`，并满足有效家长绑定关系。

对于迁移期间尚未改造、只读取 `request.user.role_type` 的代码，认证层可在当前请求加载的用户实例上设置非持久化会话角色以保持兼容，但禁止保存该临时值。数据库筛选 `role_type=...` 的业务查询必须改为对应的角色授权或关系查询。

## 机构成员 API 与界面

### 新增或恢复角色

机构成员新增接口接受单个 `role`，但以 `(institution, user, role)` 幂等创建或恢复：

- 已存在相同 active 角色：返回明确的“角色已存在”成功结果。
- 已存在 inactive 角色：恢复为 active。
- 用户已有其他机构角色：新增第二条角色关系，不覆盖原角色。
- 新增 `teacher`：同时幂等授予全局教师角色。
- 新增机构 `admin`：不授予全局系统管理员。

### 列表与编辑

成员列表按用户聚合，示例：

```json
{
  "user_id": "...",
  "user_name": "User9181",
  "roles": ["admin", "teacher"],
  "status": "active"
}
```

界面行为：

- 同一用户只显示一张成员卡。
- 同时显示“机构管理员”“教师”两个标签。
- 编辑弹窗使用两个复选框，可分别增加或停用机构角色。
- “系统管理员”文案改为“机构管理员”。
- “移除成员”停用该用户在本机构的全部角色，并要求确认。
- 教师科目和学段仍保存于用户教师资料中，只有选择教师角色时显示和更新。

## 兼容性

API 用户对象在迁移期同时返回：

```json
{
  "roles": ["admin", "teacher"],
  "active_role": "teacher",
  "role_type": "teacher"
}
```

前端逐步以 `active_role` 和 `roles` 为准，保留 `role_type` 是为了避免一次性破坏现有导航、组件和本地缓存。

现有单角色用户迁移后仍只看到一个可用角色，登录体验不变。

## 错误处理

- 登录或切换未授权角色：403，`ROLE_NOT_GRANTED`。
- 目标角色值非法：400，`INVALID_ROLE`。
- 机构角色重复添加：幂等成功，并返回当前聚合成员数据。
- 无权限修改机构成员：403，不暴露成员详细信息。
- 被撤销角色的旧令牌：认证失败，要求重新选择有效角色登录。
- 机构成员更新使用事务，避免机构关系已写入但全局教师授权失败。

## 测试与验收

### 后端

- 数据迁移为每类现有关系正确补充角色，重复执行不产生重复记录。
- 管理员账号添加教师后同时保留 `admin` 和 `teacher`。
- 同一机构的管理员与教师关系可并存，列表只返回一个聚合成员。
- 重复添加相同机构角色保持幂等。
- 机构管理员不会获得系统管理员角色。
- 加入班级自动授予学生角色；有效家长绑定自动授予家长角色。
- 未授权角色不能登录或切换，登录参数不能提升权限。
- admin 与 teacher 两组并发令牌分别通过对应权限且互不覆盖。
- refresh token 保留 active role；角色撤销后旧令牌失效。
- 现有机构、班级、任务、学生和家长权限测试无回归。

### 前端

- 成员卡正确显示多个机构角色标签。
- 编辑复选框可独立添加和停用机构管理员/教师角色。
- 登录页对未授权角色显示明确提示。
- 角色切换菜单只显示已授权角色，并跳转到正确首页。
- 本地用户缓存同时保存 `roles`、`active_role` 和兼容 `role_type`。
- UniApp H5 构建通过。

### 验收场景

手机号 `13316529181` 当前拥有系统管理员角色及机构管理员关系。在机构界面添加教师后：

1. 保存成功并刷新。
2. 成员卡同时显示“机构管理员”和“教师”。
3. 账号以管理员角色登录可进入系统管理界面。
4. 账号以教师角色登录可进入教师工作台并访问其机构。
5. 管理员会话和教师会话可以同时保持，不会互相改变角色。

## 范围边界

- 本次只修改 `./front`。
- 不把机构管理员自动提升为系统管理员。
- 不在第一版增加复杂的角色审批、角色有效期或角色变更历史页面。
- 不因删除某一个业务关系自动撤销全局角色。
- 不修改 AI 调用、试卷解析或其他无关业务。
