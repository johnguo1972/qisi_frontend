# 题库“关联题”功能设计

## 目标

将题库管理中每题的“类似题”操作改为“关联题”。教师可在弹窗中查看已关联题，并从符合规则的候选题中多选建立人工关联关系。

## 范围

- 仅修改 `front` 内的 Django 后端、UniApp 题库页面、测试和数据库迁移。
- 本次不提供解除关联、自动 AI 推荐关联或跨学科关联。

## 数据模型

新增 `QuestionRelation` 表：

| 字段 | 说明 |
| --- | --- |
| `id` | UUID 主键 |
| `question_left` | 关联对中 UUID 较小的题目 |
| `question_right` | 关联对中 UUID 较大的题目 |
| `created_by` | 建立关联的用户 |
| `created_at` | 建立时间 |

`question_left` 与 `question_right` 设联合唯一约束；服务层把任意两个题目规范为同一固定顺序，因此一对题只保存一行，但查询任意一端均可得到另一端，形成逻辑双向关系。服务层拒绝题目关联自身。

## 接口契约

接口遵循既有题库 API 的认证、题目可见性和响应封装规则。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/questions/{id}/relations/` | 返回已关联题，支持分页 |
| `GET` | `/api/v1/questions/{id}/relation-candidates/` | 返回可关联候选题，支持分页 |
| `POST` | `/api/v1/questions/{id}/relations/` | 批量建立关联，负载为 `{"question_ids": ["..."]}` |

候选题必须同时满足：

1. 题目不是原题且尚未关联；
2. `subject` 与原题一致；
3. 两题均有具体难度，且候选题难度位于原题难度的闭区间 `[difficulty - 0.5, difficulty + 0.5]`；
4. 两题至少存在一个相同标准知识点。

知识点字段为历史兼容的 JSON 数据。候选筛选服务先把每个知识点规范为稳定键：优先使用知识点 ID，其次 `module`，最后名称；再比较集合交集。这让旧字符串结构、对象结构和当前标准知识点结构都能参与匹配。查询先按学科和难度范围缩小数据库集合，再在服务层判断知识点交集，避免依赖某一 JSON 结构的 PostgreSQL 专有查询。

候选和已关联题统一返回：题目 UUID、题号、题干摘要、难度、知识点摘要；候选结果额外返回共同知识点名称。分页默认 50 条，并返回总数。

## 前端交互

1. `QuestionDetailCard` 的“类似题”按钮改名为“关联题”。
2. 点击后打开带遮罩的弹窗，右上角有关闭按钮；默认页签为“可关联题”。
3. “可关联题”展示候选列表及每行复选框；可跨页保留已选 UUID。
4. 点击“关联”时提交全部已选 UUID；成功后显示提示、清空选择、刷新两个页签并切换到“已关联题”。
5. “已关联题”仅展示已建立关系的题目；本次不提供解除操作。
6. 缺少难度或知识点时，候选页显示“当前题目缺少难度或知识点，无法生成可关联题”，而非返回误导性的候选结果。

## 权限与一致性

- 读取候选和已关联题沿用题库题目读取权限。
- 创建关联沿用当前教师题库管理权限；管理员遵循同一授权规则。
- 批量创建使用事务与数据库唯一约束，重复请求幂等；响应包含新建数量、已存在数量和无效 UUID。

## 错误处理

- 原题不存在：404。
- 关联自身或候选题不存在：不创建该关系，并在批量响应返回无效项。
- 原题缺少 `subject`、`difficulty` 或可识别知识点：候选接口返回空结果及可读原因。
- 接口失败：前端保留当前弹窗和选择状态，并显示错误提示。

## 验证

- 模型测试：双向查询、顺序规范化、联合唯一、拒绝自身关联。
- 接口测试：同学科且难度边界 `±0.5`、知识点交集、异学科排除、无交集排除、已关联排除、批量幂等。
- 页面测试/构建：按钮名称、双 Tab、勾选提交、成功后切换与刷新；执行 H5 构建。
