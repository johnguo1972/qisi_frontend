# 教师端学生添加与编辑功能可实施开发方案

## 1. 文档信息

- 需求日期：2026-09-10
- 适用端：教师端 H5 / uni-app
- 需求页面：教师端学生管理页面、`/pages/teacher/class-detail?classId=...&view=students`
- 文档性质：开发实施方案
- 当前状态：仅完成方案整理，未修改业务代码

## 2. 需求概述

在教师端学生管理页面增加“添加学生”能力，并扩展现有学生编辑能力。

教师点击“添加学生”后，打开添加学生弹窗。表单包含：

| 字段 | 必填 | 默认值或选项 |
| --- | --- | --- |
| 学生姓名 | 是 | 空 |
| 学校 | 是 | 空 |
| 年级 | 是 | 当前班级年级；下拉选择教师管理的班级年级 |
| 班级 | 是 | 当前班级；下拉选择教师管理的班级 |
| 班型 | 否 | `S班`、`A+班`、`A班` |
| 学生手机号 | 是 | 空 |
| 家长姓名 | 否 | 空 |
| 家长手机号 | 否 | 空 |

确认后需要完成：

1. 学生自动绑定到指定班级和年级。
2. 学生手机号自动注册或开通学生角色。
3. 家长手机号自动注册或开通家长角色。
4. 学生与家长自动建立有效绑定关系。
5. 添加成功后刷新当前页面的学生列表。
6. 学生编辑弹窗增加学校、年级、班级、班型、学生手机号、家长手机号等字段。

| 项目 | 现状 | 建议 |

| 学生学校 | `user_account` 中不存在 | 新增 `UserAccount.school` |

## 4. 推荐数据模型设计

### 4.1 `UserAccount` 增加学校字段

建议新增：

```python
school = models.CharField(
    max_length=100,
    blank=True,
    null=True,
)
```

学校属于学生基础档案，和姓名、手机号、当前年级放在用户账号中，方便学生端和家长端复用。

建议新增迁移：

```text
apps/accounts/migrations/0007_useraccount_school.py
```

### 4.2 `ClassStudent` 增加班型字段

建议新增：

```python
class_type = models.CharField(
    max_length=20,
    blank=True,
    null=True,
)
```

班型属于学生在某个班级中的属性，同一学生在不同班级中可能拥有不同班型，因此不建议放在 `UserAccount`。

建议新增迁移：

```text
apps/institutions/migrations/0005_classstudent_grade_and_class_type.py
```

班型建议使用稳定编码，接口返回时再映射成中文：

| 编码 | 显示值 |
| --- | --- |
| `S` | S班 |
| `A_PLUS` | A+班 |
| `A` | A班 |

### 4.3 年级和班级的归属

本次建议继续复用现有字段：

- 学生当前年级缓存：`UserAccount.grade_level`
- 学生在指定班级的年级：`ClassStudent.grade_level`
- 班级年级：`Class.grade_level`
- 学生所属班级：`ClassStudent.class_obj`

添加和编辑时，前端从教师管理的班级数据生成年级下拉选项。后端应校验所选年级与目标班级年级一致，避免出现“八年级学生绑定九年级班级但年级仍为八年级”的不一致数据。

本方案已确定增加 `ClassStudent.grade_level` 作为关系快照，具体以第 15.1 节和第 15.2 节为准。

### 4.4 家长绑定关系

现有 `StudentParentBind` 已包含：

- 学生账号
- 家长账号
- 关系类型
- 绑定状态
- 绑定时间

添加学生时默认使用：

```text
relation_type = guardian
bind_status = active
```

当前模型没有学生—家长唯一约束，而现有业务允许一个学生绑定多个家长。建议增加 `is_primary` 字段，并对每个学生的有效主家长建立唯一约束，供教师表单展示和编辑。

建议迁移时先清理重复有效绑定，再增加约束，避免迁移失败。

## 5. 后端接口方案

### 5.1 获取年级和班级选项

复用接口：

```http
GET /api/v1/classes/simple
```

返回当前教师管理的有效班级：

```json
[
  {
    "id": "班级UUID",
    "class_name": "八年级一班",
    "class_no": "CLS-xxxx",
    "grade_level": "八年级"
  }
]
```

前端处理方式：

- 班级下拉直接使用完整列表。
- 年级下拉对 `grade_level` 去重。
- 添加弹窗默认选择当前详情页班级及其年级。

后端需确认 `class_simple_list` 的查询范围覆盖当前教师作为创建人或班级教师管理的班级，并只返回 `active` 班级。

### 5.2 添加学生接口

建议新增：

```http
POST /api/v1/classes/{class_id}/students
```

请求示例：

```json
{
  "student_name": "学生姓名",
  "school": "学校名称",
  "grade_level": "八年级",
  "target_class_id": "目标班级UUID",
  "class_type": "S",
  "student_mobile": "13800000000",
  "parent_name": "家长姓名",
  "parent_mobile": "13900000000"
}
```

说明：

- URL 中的 `class_id` 表示当前页面的班级上下文。
- `target_class_id` 表示弹窗最终选中的目标班级。
- 如果不传 `target_class_id`，后端默认使用 URL 中的 `class_id`。

也可以将接口设计为统一的 `POST /api/v1/teacher/students`，把 `class_id` 完全放在请求体中；但为了复用现有班级权限校验和接口路径，本方案优先推荐扩展现有班级学生资源路径。

### 5.3 添加接口校验规则

后端必须校验：

1. 当前请求用户是教师，并且管理当前班级和目标班级。
2. 学生姓名、学校、年级、目标班级、学生手机号不能为空。
3. 学生姓名长度不超过 64 个字符。
4. 学校长度不超过 100 个字符。
5. 手机号符合 `^1[3-9]\\d{9}$`。
6. 班型只能是 `S`、`A_PLUS`、`A` 或空值。
7. 目标班级处于有效状态。
8. 目标班级未达到 `max_students` 上限；0 按不限人数处理。
9. 学生不能已是目标班级的有效成员。
10. 家长姓名单独填写但没有家长手机号时返回参数错误。
11. 学生手机号与家长手机号不能相同。
12. 已存在但被禁用或封禁的账号不应被无条件恢复，需按业务规则返回错误。

### 5.4 添加事务流程

整个流程使用 `transaction.atomic()`：

1. 锁定并校验目标班级。
2. 按学生手机号查询或创建学生账号。
3. 更新学生姓名、学校和当前年级。
4. 确保学生拥有有效的 `student` 角色。
5. 创建或恢复 `ClassStudent` 关系，设置 `join_type=manual`、`status=active` 和班型。
6. 如果填写家长手机号，按手机号查询或创建家长账号。
7. 更新家长姓名，并确保家长拥有有效的 `parent` 角色。
8. 创建或恢复 `StudentParentBind`，设置 `relation_type=guardian`、`bind_status=active`。
9. 返回完整学生列表项。

注意：现有 `get_or_create_user()` 对已存在账号不会自动增加新角色，因此不能只调用该方法完成本需求。对已有账号需要显式调用 `grant_user_role()`，同时不能覆盖其原有角色。

## 6. 学生编辑接口方案

扩展现有接口：

```http
PATCH /api/v1/classes/{class_id}/students/{student_id}
```

请求示例：

```json
{
  "student_name": "新姓名",
  "school": "新学校",
  "grade_level": "九年级",
  "target_class_id": "目标班级UUID",
  "class_type": "A_PLUS",
  "student_mobile": "13800000001",
  "parent_mobile": "13900000001"
}
```

处理规则：

- 学生姓名、学校、年级、学生手机号更新到 `UserAccount`。
- 班型更新到 `ClassStudent`。
- 修改班级时，校验目标班级归当前教师管理。
- 目标班级没有该学生时，将原关系标记为 `removed`，再创建或恢复目标关系。
- 修改学生手机号时检查 `UserAccount.mobile` 唯一性。
- 修改家长手机号时，创建或恢复新的主家长绑定。
- 家长手机号清空时，解除当前主家长关系，但不删除其他已有家长关系。

如果暂不增加 `is_primary`，则必须在接口文档中明确“编辑时使用学生的第一条有效家长绑定”，但不推荐这种隐式规则。

## 7. 学生列表接口调整

扩展 `ClassStudentSerializer`，建议返回：

```json
{
  "id": "关系UUID",
  "student": "学生UUID",
  "student_name": "学生姓名",
  "student_mobile": "13800000000",
  "school": "学校",
  "grade_level": "八年级",
  "class_id": "班级UUID",
  "class_name": "八年级一班",
  "class_type": "S",
  "parent_id": "家长UUID",
  "parent_name": "家长姓名",
  "parent_mobile": "13900000000",
  "join_type": "manual",
  "status": "active"
}
```

查询时应使用 `select_related('student', 'class_obj')`，并预加载主家长及其账号，避免序列化家长信息时产生 N+1 查询。

手机号在列表中继续脱敏展示，编辑弹窗可根据接口返回值回显完整手机号，或按安全要求改为单独查询并只允许重新输入。

## 10. 权限、安全与一致性要求

- 所有添加、编辑、班级迁移操作必须验证教师是否管理目标班级。
- 不能仅依赖前端传入的班级 ID。
- 学生手机号和家长手机号均为账号唯一标识，修改前必须做唯一性校验。
- 已存在账号增加角色时，不得覆盖原有 `role_type` 或其他角色。
- 添加学生、创建家长、建立绑定、创建班级关系必须在同一事务中完成。
- 家长绑定直接设置为 `active`，因为该绑定由教师后台人工确认完成。
- 返回学生列表时，手机号默认脱敏。
- 建议记录创建人、修改人和操作时间；如果暂不新增审计表，至少保留现有账号和关系的更新时间。

## 15. 修订版执行口径（以本节为准）

### 15.1 最终数据字段

`UserAccount` 新增：

```python
school = models.CharField(max_length=100, blank=True, null=True)
```

`ClassStudent` 新增：

```python

```

其中：

- `ClassStudent.grade_level` 是学生与指定班级关系上的年级，满足“绑定班级和年级”。
- `UserAccount.grade_level` 继续保留，作为学生当前年级缓存；新增或编辑时同步更新。
- `ClassStudent.class_type` 保存班型编码：`S`、`A_PLUS`、`A`。
- `UserAccount.school` 保存学生学校。
- 家长姓名和手机号继续使用家长账号的 `display_name`、`mobile`。

### 15.2 最终迁移文件

必须新增以下迁移，不能只修改 Model：

```text
apps/accounts/migrations/0007_useraccount_school.py
apps/accounts/migrations/0008_studentparentbind_primary.py
apps/institutions/migrations/0005_classstudent_grade_and_class_type.py
```

`0008_studentparentbind_primary.py` 必须完成：

1. 为 `StudentParentBind` 增加 `is_primary` 布尔字段。
2. 检查并清理已有重复有效绑定。
3. 为每个学生选出一条主家长关系。
4. 增加“每个学生最多一条有效主家长”的 PostgreSQL 条件唯一约束。

如果本次明确不支持主家长概念，则必须删除方案中所有 `is_primary` 设计，并将编辑接口改为接收 `parent_id`；不能保留“取第一条绑定”的隐式逻辑。本方案采用主家长设计。

### 15.3 最终添加接口

继续使用现有学生集合路径：

```http
GET  /api/v1/classes/{class_id}/students
POST /api/v1/classes/{class_id}/students
```

因此 `class_views.py` 中的视图装饰器必须由：

```python
@api_view(['GET'])
```

改为：

```python
@api_view(['GET', 'POST'])
```

`class_id` 表示当前页面班级上下文，`target_class_id` 表示弹窗选中的目标班级。后端必须同时校验当前教师管理这两个班级；未传 `target_class_id` 时使用 URL 中的 `class_id`。

添加成功后的页面规则固定为：

- 目标班级等于当前班级：重新加载当前学生列表，新学生必须显示。
- 目标班级不同于当前班级：接口返回目标班级信息，前端跳转到目标班级详情页并重新加载目标班级学生列表，同时提示“已添加到目标班级”。

这样既支持班级下拉选择，也不会错误地把学生显示在未绑定的当前班级中。

### 15.4 最终请求字段映射

前端提交字段及后端落库位置必须固定如下：

| 请求字段 | 数据库位置 |
| --- | --- |
| `student_name` | `UserAccount.display_name` |
| `student_mobile` | `UserAccount.mobile` |
| `school` | `UserAccount.school` |
| `grade_level` | `ClassStudent.grade_level`，并同步 `UserAccount.grade_level` |
| `target_class_id` | `ClassStudent.class_obj_id` |
| `class_type` | `ClassStudent.class_type` |
| `parent_name` | 家长 `UserAccount.display_name` |
| `parent_mobile` | 家长 `UserAccount.mobile` |

序列化器不能直接把 `student_name`、`student_mobile` 当作 Model 字段，需要使用显式 Serializer 字段或单独的添加/编辑 Serializer 完成映射。

### 15.5 家长字段规则

添加和编辑表单中，家长姓名、家长手机号必须成对填写：

- 两者都为空：不创建或不修改家长绑定。
- 两者都填写：创建或复用家长账号，并建立 `guardian` / `active` / `is_primary=true` 关系。
- 只填写其中一个：返回 400 参数错误。
- 学生手机号和家长手机号相同：返回 400 参数错误。
- 更换家长：取消旧主家长标记，保留历史关系；新关系设为主家长。
- 清空家长信息：解除当前主家长关系，但不删除其他家长历史数据。

### 15.6 最终添加事务

添加接口和编辑接口均必须使用 `transaction.atomic()`，并按以下顺序执行：

1. 锁定并校验目标班级及班级容量。
2. 锁定学生手机号对应的账号；不存在则创建学生账号。
3. 更新学生姓名、学校和学生当前年级。
4. 显式授予 `student` 角色，不覆盖账号已有角色。
5. 创建或恢复 `ClassStudent`，保存关系年级和班型。
6. 如果有家长信息，锁定或创建家长账号。
7. 显式授予 `parent` 角色，不覆盖账号已有角色。
8. 创建或恢复主家长绑定。
9. 返回完整学生列表项。

班级容量检查必须与班级行锁在同一事务中完成，避免并发添加突破人数上限。手机号唯一冲突、重复成员、角色冲突和数据库约束异常都必须转换为明确的 4xx 错误，不得返回 500。

### 15.7 最终编辑规则

现有 `PATCH /api/v1/classes/{class_id}/students/{student_id}` 不能继续只处理 `display_name`，必须完整处理本节 15.4 的字段。

当 `target_class_id` 改变时：

1. 校验目标班级归当前教师管理。
2. 校验目标班级不存在该学生有效关系。
3. 原 `ClassStudent` 标记为 `removed`。
4. 创建或恢复目标班级关系。
5. 保存目标班级关系的年级和班型。

学生手机号修改前必须检查 `UserAccount.mobile` 唯一性；已有禁用或封禁账号不得被自动恢复。

### 15.8 必须同步修复的现有问题
