## 3. 迁移文件管理规则

### 3.1 必须遵守的规则

| 规则 | 说明 | 原因 |
|------|------|------|
| **迁移文件必须提交到Git** | `migrations/00XX_xxx.py` 必须 commit + push | 其他同事和服务器依赖这些文件执行迁移 |
| **不要手动修改迁移文件** | 除非你明确知道在做什么 | 可能导致迁移历史不一致 |
| **不要删除已提交的迁移文件** | 已 push 的迁移文件不能删除 | 会导致其他同事的迁移链断裂 |
| **每次改模型都要生成迁移** | 改了 `models.py` 就必须 `makemigrations` | 遗漏会导致线上数据库与代码不一致 |
| **本地先 migrate 再 push** | 确保迁移文件能正确执行 | 避免推了无法执行的迁移文件 |

### 3.2 禁止操作

```bash
# ❌ 禁止：删除迁移文件后重新生成
rm apps/study/migrations/0005_xxx.py
python manage.py makemigrations study
# 这会导致迁移历史断裂！

# ❌ 禁止：手动编辑已提交的迁移文件
# 除非你是团队中唯一开发且明确知道后果

# ❌ 禁止：跳过迁移直接改数据库
# ALTER TABLE ...  # 这样Django不知道表结构变了

# ❌ 禁止：不同分支生成同名迁移文件
# 会导致合并冲突
```

### 3.3 迁移文件冲突处理

当两个同事同时改了模型，可能产生迁移文件冲突：

```bash
# 场景: 同事A生成了 0005_a.py，同事B生成了 0005_b.py
# 合并时冲突

# 解决方法:
# 1. 先拉取对方代码
git pull

# 2. 删除自己生成的冲突迁移文件
rm apps/study/migrations/0005_b.py

# 3. 基于最新代码重新生成
python manage.py makemigrations study

# 4. Django会自动生成正确序号的迁移文件（如 0006_b.py）
# 5. 测试本地迁移
python manage.py migrate

# 6. 提交
git add apps/study/migrations/
git commit -m "fix: 解决迁移文件冲突"
git push
```

## 4. 数据库备份（迁移前必须执行）

### 4.1 本地数据库备份

```bash
# PostgreSQL
pg_dump -U postgres -d qisi_db > backup_$(date +%Y%m%d_%H%M%S).sql

# 或使用 Django 命令
python manage.py dumpdata --natural-foreign --natural-primary -e contenttypes -e auth.Permission > backup_$(date +%Y%m%d).json
```

### 4.2 服务器数据库备份

```bash
# 在服务器上执行

# 方式1: PostgreSQL dump
pg_dump -U postgres -d qisi_db | gzip > /backups/qisi_db_$(date +%Y%m%d_%H%M%S).sql.gz

# 方式2: 使用项目已有的备份脚本（如果有）
# 查看 db_backups/ 目录
ls db_backups/

# 方式3: Docker 环境
docker exec postgres pg_dump -U postgres qisi_db | gzip > backup.sql.gz
```

### 4.3 迁移失败回滚

```bash
# 如果迁移执行失败，回滚到上一个版本

# 查看当前迁移状态
python manage.py showmigrations

# 回滚 study app 到上一个迁移
python manage.py migrate study 0004  # 回退到 0004

# 回滚 parser app 到上一个迁移
python manage.py migrate parser 0011  # 回退到 0011

# 恢复数据库备份（如果回滚也不够）
psql -U postgres -d qisi_db < backup_20260727.sql
```

## 7. 常见问题排查

### Q1: `makemigrations` 提示 "No changes detected"

```bash
# 原因: models.py 的修改没有被 Django 识别
# 解决: 确认 App 在 INSTALLED_APPS 中

# 检查 config/settings.py
INSTALLED_APPS = [
    ...
    'apps.study',
    'apps.parser',
    ...
]

# 如果已注册但仍不识别，尝试指定 app 名称:
python manage.py makemigrations study parser
```

### Q2: `migrate` 报错 "relation already exists"

```bash
# 原因: 表已经存在（可能之前手动创建过）
# 解决: 使用 --fake 标记迁移为已执行

python manage.py migrate study 0005 --fake
python manage.py migrate parser 0012 --fake
```

### Q3: 同事拉取代码后 migrate 报错 "dependency not found"

```bash
# 原因: 迁移文件不完整，缺少依赖迁移
# 解决: 确保所有迁移文件都已提交

# 开发者A检查:
git log --oneline -- apps/study/migrations/ apps/parser/migrations/

# 确保所有 00XX 文件都在 Git 中
git ls-files apps/study/migrations/
git ls-files apps/parser/migrations/
```

### Q4: 服务器 migrate 后服务启动失败

```bash
# 原因: 可能是新字段导致的序列化问题
# 解决: 检查 serializers.py 是否需要更新

# 查看错误日志
sudo journalctl -u qisi -n 50
# 或
tail -f logs/gunicorn.log

# 常见原因:
# - QuestionDetailSerializer 需要添加新字段到 fields 列表
# - QuestionListSerializer 需要添加新字段
```

### Q5: 迁移后旧数据的 tags 字段为空

```bash
# 这是正常的！tags 字段默认值为 []（空列表）
# 旧题目需要后续通过 API 或管理后台添加标签

# 如果需要批量设置默认标签:
python manage.py shell
>>> from apps.parser.models import ExamQuestion
>>> ExamQuestion.objects.filter(tags__isnull=True).update(tags=[])
```

## 8. Django 迁移命令速查表

| 命令 | 作用 |
|------|------|
| `python manage.py makemigrations` | 检测模型变更并生成迁移文件 |
| `python manage.py makemigrations study parser` | 仅为指定App生成迁移 |
| `python manage.py migrate` | 执行所有未应用的迁移 |
| `python manage.py migrate study` | 仅执行 study 的迁移 |
| `python manage.py migrate study 0004` | 回滚 study 到 0004 |
| `python manage.py showmigrations` | 查看所有迁移状态 |
| `python manage.py showmigrations study` | 查看 study 的迁移状态 |
| `python manage.py sqlmigrate study 0005` | 查看迁移对应的SQL语句 |
| `python manage.py migrate --fake` | 标记迁移为已执行（不实际执行） |
| `python manage.py migrate --fake-initial` | 首次迁移时跳过已存在的表 |
| `python manage.py dbshell` | 进入数据库命令行 |
