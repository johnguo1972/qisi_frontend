# 学生端固定式与非固定式引导优化实施方案

## 1. 方案目的

本文针对学生端固定式引导和非固定式引导当前存在的响应慢、AI 不可用、答案判断不准确、错因分析不足和引导不够智能等问题，提出可落地的修复与优化方案。

目标是让学生答错题目后能够快速进入引导，并根据学生的实际回答准确识别错因、提供针对性提示和解决问题的方法。

本文为实施方案，仅整理方案，不包含代码修改。

## 2. 总体设计原则

采用“引导内容提前准备、学生回答后单次分析、记录完成后推进”的架构：

```text
题目导入/教师审核
    ↓
准备已有的 B/C 引导步骤、题目上下文和图像事实
    ↓
学生进入引导：优先读取已有内容，快速展示
    ↓
学生回答一句
    ↓
仅调用一次 qwen3.7-flash
    ↓
分析回答、判断错因、生成纠正方向
    ↓
将回答、对话、错因和评价写入已有会话记录
    ↓
再返回下一个问题
```

核心原则：

1. 学生进入引导页面时不等待长时间的完整 AI 生成。
2. 进入页面和生成引导步骤不执行同步的完整 AI 生成，保证首屏快速可用。
3. 学生每回答一句，只执行一次 qwen3.7-flash 调用；该调用同时完成回答评价、错因判断和下一步引导内容生成，不再为“评价”和“下一问”分别调用模型。
4. 错因分析发生在对话过程中，不在学生回答前预先生成；分析结果和完整对话写入已有会话记录后，才进入下一问题。
5. 图像题优先使用已经准备好的视觉事实，避免在回答后额外调用视觉模型。
6. AI 失败时不伪造评价、不错误推进、不向学生暴露内部异常。

## 3. 模式职责划分

### 3.1 固定式引导：B 模式

B 模式用于将复杂题目拆分成若干个有明确选项的认知步骤。

主要职责：

- 帮助学生识别题目已知条件。
- 帮助学生选择正确公式、定理或解题方向。
- 帮助学生检查计算和结论。
- 在学生提交选项后，结合当前步骤、所选答案和题目上下文，额外调用 AI 判断学生实际错因。

建议的处理方式：

```text
学生选择选项
    ↓
程序提取选项标签
    ↓
判断对错
    ↓
调用一次 qwen3.7-flash 分析本轮回答和错因
    ↓
写入对话与错因记录
    ↓
返回下一问题或纠正方向
```

B 模式进入页面时只读取固定引导内容，不调用 AI 做学生错因分析；学生提交每个步骤的回答后，统一额外调用一次 `qwen3.7-flash`，完成该次回答的评价、错因判断和纠正方向，然后记录并进入下一步骤。

### 3.2 非固定式引导：C 模式

C 模式用于理解学生的自然语言回答，并根据学生的具体思路进行动态引导。

主要职责：

- 判断学生是否理解当前知识点。
- 识别概念错误、读图错误、计算错误和条件遗漏。
- 对部分正确的回答补充缺失内容。
- 针对错误回答判断用户的错误原因，并给出针对性的纠正方向。
- 将用户本轮对话、回答、错因、评价和纠正方向写入已有数据库会话记录。
- 完成记录后，根据本轮结果生成或选择下一步问题。

C 模式学生回答后的动态评价、错因判断和下一步引导统一使用 `qwen3.7-flash`。

## 4. B 模式优化方案

### 4.1 修复选项标签比较

当前前端可能提交完整选项文本：

```text
A. 分析已知条件，找出关键信息
```

而后端保存的正确答案通常只有：

```text
A
```

后端应统一将学生回答标准化为选项标签：

```text
A. xxx → A
B. xxx → B
C. xxx → C
D. xxx → D
```

同时兼容直接提交 `A`、`B`、`C`、`D` 的情况。

### 4.2 不扩展题目引导数据结构

B 模式的固定问题、选项、正确答案和下一步骤仍使用现有引导数据，不需要预先增加“错因”字段，也不要求在题目导入或进入引导前由 AI 生成学生错因。

错因不是题目静态属性，而是学生本轮回答后的动态分析结果。应使用现有的学生引导会话记录（例如现有 `content_log_json` 或已有答题记录）保存本轮学生回答、AI 评价、错因和纠正方向。这样既能保留学生实际对话过程，也不会把某个学生的错误原因错误地固化到题目数据中。

### 4.3 B 模式“程序判定 + 单次 AI 错因分析”

B 模式的选项对错由后端程序完成，学生回答后再由 AI 分析原因：

- 解析选项标签。
- 判断 `correct_option`。
- 根据程序判定结果确定本轮是否正确。
- 调用一次 `qwen3.7-flash`，输入当前固定问题、选项、正确答案、学生选择以及必要的题目上下文。
- 由这一次调用返回面向学生的评价、动态错因、针对性的纠正方向和下一步问题/提示。
- 将学生选择和 AI 分析结果写入现有会话记录。
- 完成记录后再返回下一步骤；不能先推进步骤再补写分析。

即使学生只提交了选项标签，也应让模型结合选项语义和当前步骤判断可能的认知错误；如果没有足够证据，应返回“无法确定”并给出最小澄清提示，不能把猜测当成确定错因。B 模式每次学生回答最多调用一次模型，不再拆分为多次 AI 调用。

### 4.4 B 模式缺少数据时的处理

如果 `ai_answer_b` 不存在：

1. 立即返回现有的固定步骤或与题型相关的通用兜底步骤。
2. 不在学生请求中同步生成完整 B 内容。
3. 后台补齐或修复已有的 B 模式引导内容。
4. 下次进入时优先读取已经准备好的内容。

兜底内容应尽量按照题型区分，不能所有题目都使用相同的泛化话术。

## 5. C 模式优化方案

### 5.1 评价请求必须包含完整上下文

C 模式评价不能只传递原题题干、原题答案和学生回答，还需要传入当前步骤上下文：

```json
{
  "question": {
    "stem": "某物体的 s-t 图像如图所示……",
    "options": ["A...", "B...", "C...", "D..."],
    "analysis": "完整解析"
  },
  "visual_facts": [
    "0~3s：路程由0m增加到12m",
    "3~6s：路程保持12m不变",
    "6~9s：路程由12m增加到18m"
  ],
  "current_step": {
    "question": "s-t 图像中图线斜率代表哪个物理量？直线说明什么运动状态？",
    "reference_answer": "斜率代表速度，倾斜直线表示匀速直线运动",
    "key_points": [
      "斜率表示速度",
      "倾斜直线表示速度不变"
    ],
    "followup_hint": "请结合纵坐标变化量和时间变化量继续思考。"
  },
  "history": [],
  "student_answer": "匀速运动"
}
```

### 5.2 C 模式“单次调用完成分析和下一问”

学生提交一句回答后，只调用一次 `qwen3.7-flash`。这一次调用必须同时完成：判断回答是否正确、识别错因、给出针对性的纠正方向、形成面向学生的评价，并生成或选择下一步问题。不能先调用一次做评价，再调用一次生成下一问题。

建议模型返回：

```json
{
  "result": "partial",
  "error_type": "答案不完整",
  "evaluation": "你已经判断出物体做匀速运动，但还没有说明图线斜率代表速度。",
  "correction_direction": "先明确 s-t 图像斜率的定义，再结合纵坐标变化量和时间变化量判断物理量。",
  "next_question": "s-t 图像中纵坐标变化量与时间变化量的比值表示什么？",
  "next_hint": "请结合纵坐标变化量和时间变化量继续思考。",
  "confidence": 0.94
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `result` | `correct`、`partial`、`incorrect`、`unclear` |
| `error_type` | 概念错误、读图错误、计算错误、条件遗漏、表达不完整等 |
| `evaluation` | 面向学生的简短评价 |
| `correction_direction` | 针对本轮错误原因给出的纠正方向，不直接替学生完成整道题 |
| `next_question` | 完成本轮记录后展示给学生的下一问题 |
| `next_hint` | 不直接给出答案的下一步提示 |
| `confidence` | 模型判断置信度 |

### 5.3 C 模式根据单次分析结果推进

模型在一次响应中返回结果，服务端完成记录后按照结果选择下一问题。学生仍然可以进行多个引导步骤，但每个学生回答只触发一轮模型调用，不进行同一回答的多轮追问或多模型串联。

建议采用以下规则：

| 判断结果 | 处理方式 |
| --- | --- |
| 正确 | 记录本轮结果后进入下一知识点或下一步骤 |
| 部分正确 | 记录缺失点和纠正方向，下一问题围绕缺失点设计 |
| 概念错误 | 记录概念错因，下一问题做概念辨析 |
| 读图错误 | 记录读图错因，下一问题聚焦图像关键事实 |
| 计算错误 | 记录公式、单位或计算错因，下一问题要求检查对应环节 |
| 条件遗漏 | 记录遗漏条件，下一问题引导重新寻找已知条件 |
| 答非所问 | 记录表达偏差，下一问题重新限定回答范围 |
| 无法判断 | 记录证据不足，下一问题要求学生补充最小必要信息 |

不能在未完成本轮分析和记录前无条件执行：

```text
step_index = step_index + 1
```

下一问题可以使用模型返回的 `next_question`，也可以从现有固定步骤中选择；两种情况都必须发生在本轮对话和错因记录成功之后。

### 5.4 AI 评价失败时不推进步骤

如果本轮唯一的 `guidance_evaluate` 请求失败：

1. 保存学生本次回答。
2. 保留当前步骤索引。
3. 返回 `retryable: true`。
4. 前端显示“暂时无法完成评价，请稍后重试”，不显示内部异常名。
5. 不自动发起第二次模型调用，不推进到下一步骤。
6. 若业务必须保证不中断，只能使用当前步骤已有的静态兜底提示；该兜底不能冒充 AI 错因分析，且应记录降级状态。

不能在 AI 评价失败后直接返回下一道问题，否则会造成学生没有得到错因反馈就被推进。学生后续主动重新提交时，才视为新的一轮回答处理。

## 6. 图像题处理方案

图像题应采用“提前读图、实时使用事实”的方式：

```text
qwen3-vl-plus 读取题图
    ↓
提取图中的客观事实
    ↓
保存 ai_vision_extract
    ↓
qwen3.7-flash 使用视觉事实分析学生回答
```

实时回答分析阶段只传递结构化视觉事实，不重复上传原图，也不再额外调用视觉模型；本轮唯一模型调用仍为 `qwen3.7-flash`。

例如 s-t 图应提前保存：

```text
0~3s：路程增加到12m
3~6s：路程保持12m
6~9s：路程增加到18m
```

这样可以减少网络传输和模型读图耗时，提高图像题判断稳定性。

## 7. 模型和任务配置建议

### 7.1 实时任务

| 配置项 | 建议值 |
| --- | --- |
| 模型 | `qwen3.7-flash` |
| temperature | 0～0.2 |
| max_tokens | 512～1024 |
| timeout | 8～15 秒 |
| retry_count | 0 次（不自动重试） |
| 并发等待 | 2～5 秒 |
| response_format | JSON |

实时任务包括：

- B 模式学生选项回答后的评价和错因分析。
- C 模式学生自然语言回答后的评价和错因分析。
- 针对错误原因的纠正方向。
- 下一步问题或短引导。

上述内容必须由同一次模型调用返回，服务端在写入会话记录后再返回下一问题。

### 7.2 离线任务

离线任务可以根据准确率和成本选择模型：

- 学生回答后的 B/C 分析、错因判断、纠正方向和下一问题：统一使用 `qwen3.7-flash`。
- 图像事实提取：现有 `qwen3-vl-plus` 只用于离线或题目资料准备阶段，不参与学生每次回答后的实时链路。
- 引导步骤准备：优先使用现有固定内容或后台预生成内容；如果需要 AI 生成文字引导，也应优先使用 `qwen3.7-flash`，并在学生进入页面时避免同步等待。

`qwen3.7-plus` 不作为本需求的学生端实时引导模型。是否在后台审核或复杂题目处理中使用，应单独评估，不能混入学生回答后的单次实时调用链路。

## 8. 预生成和缓存方案

### 8.1 生成时机

建议在以下时机准备 B/C 引导步骤和题目上下文：

1. 题目导入完成后。
2. 教师审核题目后。
3. 教师修改题干、选项、答案或解析后。
4. 题图重新裁剪后。
5. 发现引导内容缺失时，由后台补齐，不阻塞学生进入页面。

### 8.2 缓存内容

缓存的内容仅是题目和引导步骤的静态准备数据，不包含某个学生尚未回答时的错因。应至少包含：

- 题目 ID。
- 题目内容版本。
- 引导模式。
- 模型名称。
- 引导步骤和题目上下文。
- 视觉事实版本。
- 生成状态。
- 生成时间。

题目内容发生变化后，应根据题目版本或上下文哈希自动使旧引导失效。学生回答后的错因、评价和对话记录写入现有学生会话记录，不写回题目静态引导数据。

### 8.3 学生进入页面时的策略

```text
存在有效缓存 → 立即展示
没有缓存 → 立即展示规则化兜底问题
          ↓
       后台生成正式内容
```

## 9. 错误处理和监控方案

服务端需要记录：

- `session_id`
- `question_id`
- `mode`
- `step_index`
- `trace_id`
- provider 和 model
- 请求耗时
- HTTP 状态码
- 重试次数
- 错误类型
- 是否发生降级

每次学生回答还应记录本轮完整对话、程序判定结果、AI 错因、纠正方向、评价和下一问题。优先复用现有会话日志字段，不新增题目侧的错因数据结构。

错误应区分：

```text
配置错误
网络错误
请求超时
429 限流
5xx 服务异常
并发资源不足
响应格式错误
业务上下文错误
```

前端不显示 `AIRequestError`、`AIResponseError` 等内部异常名称，只显示可理解的提示。

## 10. Session 状态处理

### 10.1 正常推进

每次回答必须按以下顺序处理：

1. 读取当前步骤和必要题目上下文。
2. 接收学生回答，并执行程序可确定的判断（B 模式选项对错）。
3. 只调用一次 `qwen3.7-flash`，分析回答、判断错因、生成纠正方向和下一问题。
4. 将当前步骤、学生回答、完整对话、AI 判断结果、错因类型、评价内容、纠正方向、下一问题、请求耗时和错误状态写入现有会话记录。
5. 记录成功后再更新步骤索引并返回下一问题。

### 10.2 降级到 B 模式

C 模式降级到 B 模式时必须同步重置：

- `mode_type = B`。
- `step_index = 0`。
- B 模式当前步骤。
- B 模式答案状态。
- 前端显示状态。

确保前端显示步骤和后端实际处理步骤一致。

### 10.3 防止重复提交

需要继续保留前端提交锁，并在后端增加幂等控制，避免网络重试导致同一回答被重复记录和重复调用模型。

## 11. 推荐实施阶段

执行必须严格按照以下顺序进行，不允许跳过阶段或在阶段验收未完成前并行进入下一阶段。

### 阶段 0：基线确认和评审

执行内容：

1. 固化当前 B/C 接口样例、示例题、数据库会话记录样例和 AI 日志样例。
2. 确认接口字段、错误码、前端文案和现有 `content_log_json` 记录方式。
3. 确认测试环境的 Qwen 配置、并发限制和监控指标采集方式。

阶段门禁：

- 功能正确性：当前 B/C 基线行为和已知问题能够复现。
- 数据库记录：确认当前会话、步骤和回答记录位置。
- 单次调用：统计当前每次学生回答的实际 AI 调用次数，形成基线。
- 异常降级：复现 C 数据缺失、AI 超时和响应异常时的现有行为。
- 性能指标：记录启动接口、回复接口耗时以及 300 秒超时风险基线。
- 阶段性灰度：仅在测试环境用固定样本完成小范围验证，不进入生产。

### 阶段 1：修复确定性错误

执行内容：

1. 修复 B 模式选项文本和标签比较问题。
2. 修复 C 降级后的步骤索引问题。
3. AI 评价失败时不推进步骤。
4. 前端隐藏内部异常类型。

阶段门禁通过后，才能进入阶段 2：

- 功能正确性：B 提交 `A` 与 `A. 选项内容` 判断一致，C 降级步骤一致。
- 数据库记录：回答、当前步骤和降级状态没有错位或丢失。
- 单次调用：本阶段不引入额外重复调用；未实现新 AI 链路的路径调用次数保持基线。
- 异常降级：超时、限流、非法响应不会错误增加步骤，不暴露内部异常。
- 性能指标：确定性判断不增加明显耗时，失败请求不再等待完整长链路。
- 阶段性灰度：测试环境小范围开启，完成 B/C 固定样本回归后才允许继续。

### 阶段 2：补齐模型上下文

执行内容：

1. B/C 统一组装当前步骤上下文。
2. C 评价增加当前引导问题、参考答案和关键评分点。
3. 增加必要的历史回答、题目解析和视觉事实。
4. 不改变现有题目引导持久化结构。

阶段门禁通过后，才能进入阶段 3：

- 功能正确性：模型请求使用当前步骤参考内容，不再只使用原题答案。
- 数据库记录：上下文来源和学生回答对应正确会话及步骤，不把学生错因写入题目数据。
- 单次调用：上下文补充不产生额外模型调用，调用链路仍可计数和追踪。
- 异常降级：上下文缺失时能够明确标记并使用安全兜底，不阻塞页面。
- 性能指标：上下文长度受控，不能因传入完整历史或图片导致超时明显增加。
- 阶段性灰度：使用图像题、计算题和普通题进行小范围测试，确认上下文完整后才允许继续。

### 阶段 3：实现回答后的单次错因分析

执行内容：

1. B/C 学生回答后调用一次 `qwen3.7-flash`。
2. 返回正确、部分正确、错误和无法判断分类。
3. 返回动态错因、评价和针对性的纠正方向。
4. 将本轮对话、回答、错因和评价写入现有会话记录。
5. 不预先生成学生错因，不扩展题目引导数据结构。

阶段门禁通过后，才能进入阶段 4：

- 功能正确性：AI 能根据当前回答返回合理的评价、动态错因和纠正方向。
- 数据库记录：错因和完整对话写入现有会话记录，且记录发生在下一步骤之前。
- 单次调用：每条学生回答模型调用数严格为 1，自动重试数为 0，不存在评价/下一问串联调用。
- 异常降级：AI 失败时保存回答和失败状态，不增加步骤，不自动调用第二次模型。
- 性能指标：单次实时请求耗时达到阶段目标，能够记录请求耗时、模型和 trace_id。
- 阶段性灰度：使用标注样本验证错因准确性和纠正方向质量，通过后才允许继续。

### 阶段 4：实现记录后推进和自适应引导

执行内容：

1. 本轮分析和记录完成后，根据回答结果选择下一步骤。
2. 对部分正确、概念错误、读图错误、计算错误等情况返回针对性下一问题。
3. 对无法判断或服务异常执行安全降级。
4. 增加事务边界和幂等控制，防止重复提交重复调用。

阶段门禁通过后，才能进入阶段 5：

- 功能正确性：下一问题与学生回答和错因匹配，不能无条件推进。
- 数据库记录：回答、AI 结果、下一问题和步骤索引顺序正确，重复请求不产生重复有效记录。
- 单次调用：相同回答或相同 `reply_id` 只产生一次模型调用。
- 异常降级：失败、重复、会话冲突和 C→B 降级均保持步骤和状态一致。
- 性能指标：事务、幂等检查和记录写入不会造成明显额外延迟。
- 阶段性灰度：在测试环境模拟并发、重复点击、断网和服务失败后完成回归。

### 阶段 5：优化响应速度和资源使用

执行内容：

1. 将 B/C 引导步骤准备迁移到后台任务，学生进入页面时直接读取现有内容。
2. 增加题目上下文缓存。
3. 实时任务使用 Flash、小 Token、短超时和不自动重试。
4. 限制并发等待时间，避免继承 300 秒等待配置。

阶段门禁通过后，才能进入阶段 6：

- 功能正确性：缓存命中、缓存缺失和后台补齐三种路径都能正常进入引导。
- 数据库记录：后台准备数据和学生会话数据分离，学生错因仍写入现有会话记录。
- 单次调用：实时回答仍为每条回答一次模型调用，后台补数据不介入学生回复链路。
- 异常降级：后台任务失败不阻塞学生；实时失败不自动重试、不错误推进。
- 性能指标：启动接口基本即时，实时回复 P95 不超过 8 秒、P99 不超过 15 秒。
- 阶段性灰度：测试环境和内部用户完成性能压测及资源限流验证。

### 阶段 6：综合质量、灰度和上线验证

执行内容：

1. 建立真实物理、数学、图像题测试集。
2. 统计响应耗时、AI 不可用率、错因分类准确率和学生重答正确率。
3. 小比例学生开启新回复链路，逐步扩大范围。
4. 稳定后再关闭旧的同步 C 生成路径。

阶段 6 完成条件：

- 功能正确性、数据库记录、单次调用、异常降级全部通过验收。
- 性能指标达到第 19 节目标，且无数分钟等待。
- 灰度期间无严重数据错位、重复调用、错误推进或内部异常泄露。
- 已验证配置回滚和功能开关回滚，确认可以安全停止新链路。

## 11.1 阶段门禁规则

每个阶段结束时必须形成一份验证记录，至少包含：测试环境、代码版本、测试题目、接口请求、响应结果、数据库会话记录、AI 调用次数、异常场景、耗时指标和灰度范围。

只有六类验证全部通过，项目负责人、后端、前端和测试共同确认后，才能开始下一阶段开发：

```text
功能正确性
    + 数据库记录正确
    + 每条回答只调用一次模型
    + 异常和降级正确
    + 性能指标达标
    + 阶段性灰度通过
            ↓
       允许下一阶段
```

任一项失败时，必须停留在当前阶段修复和复测；不得以“后续阶段再补验证”为理由继续开发或上线。

## 12. 关键验收标准

### 12.1 固定式引导

- 提交 `A. xxx` 和提交 `A` 都能正确判断。
- 正确选项返回正确反馈。
- 学生提交选项后额外调用一次 `qwen3.7-flash`，根据本轮回答动态分析错因并给出纠正方向。
- 错误选项的回答、对话、错因和评价写入现有会话记录。
- 不在进入引导前预先生成学生错因，不新增题目侧错因数据结构。
- 缺少预生成数据时能够立即进入可用兜底。

### 12.2 非固定式引导

- 评价模型能获取当前引导问题。
- 评价模型能获取当前步骤参考答案和关键点。
- 图像题能使用视觉事实。
- 能区分正确、部分正确、错误和答非所问。
- 学生回答后只调用一次 `qwen3.7-flash`，同一次响应同时返回评价、错因、纠正方向和下一问题。
- 用户对话、错因等信息在返回下一问题前写入现有会话记录。
- 下一步问题会根据学生回答变化，不对同一回答进行多轮模型追问。
- AI 失败时不自动重复调用、不推进步骤，并记录降级状态。

### 12.3 性能和稳定性

- 缓存命中时进入引导页面基本即时响应。
- 正常实时评价尽量控制在 3～8 秒内。
- AI 异常时不等待数分钟。
- 服务端能够通过 trace_id 定位一次完整请求。
- 前端不显示内部异常类型。

## 13. 最终建议

优先采用以下落地策略：

```text
B 模式：现有固定问题 + 程序判断选项
       + 学生回答后调用一次 qwen3.7-flash 分析动态错因
       + 写入会话记录后返回下一问题

C 模式：现有/后台准备的引导框架
       + 学生回答后调用一次 qwen3.7-flash
       + 同时完成回答评价、错因判断、纠正方向和下一问题
       + 写入会话记录后推进

图像题：提前提取视觉事实
       + 实时 Flash 使用视觉事实进行一次回答分析
```

最优先修复 B 模式标签比较和 B/C 当前步骤上下文传递问题，然后将 B/C 的学生回答处理统一为“一次 qwen3.7-flash 调用 + 一次会话记录 + 下一问题”，再优化超时、并发和缓存。

本方案的关键边界是：错因必须来自学生本轮回答后的 AI 判断，不能在回答前预先写入题目；B 模式不增加题目引导数据结构，动态错因写入已有学生会话记录；同一条学生回答不进行多轮模型调用。

这样可以同时实现：

- 固定式引导快速、稳定、可控。
- 非固定式引导能够理解学生的自然语言回答。
- 系统能够识别具体错因。
- 系统能够提供针对性的解决方法。
- AI 服务异常时仍然可以继续学习。

## 14. 可直接实施的代码任务

本节将前面的设计转换为当前项目可以直接拆分、开发和验收的任务。任务范围仅限学生端 B/C 引导，不修改教师端引导流程，不新增数据库表或数据库模型字段。

### 14.1 后端任务：`apps/study/guidance_views.py`

1. `start_guidance`：
   - 保持现有 POST 路径、权限校验和 `code/message/data/trace_id` 返回格式。
   - B 模式继续读取 `_extract_b_mode_step` 返回的固定问题和选项。
   - C 模式优先读取 `ai_answer_c` 或会话中已有的引导步骤。
   - C 模式没有步骤时，不在学生请求中同步调用 `guidance_generate`；立即返回现有规则化 C 兜底问题，并标记 `is_fallback=true`，由后台任务补齐内容。
   - 进入页面时不执行学生错因分析，不把任何学生错因写入题目数据。

2. `guidance_reply`：
   - 保持会话归属校验、会话状态校验和题目存在性校验。
   - 从 `content_log_json.step_index` 读取当前步骤，不能直接相信前端传入的步骤。
   - B 模式先标准化选项标签，再由程序确定 `is_correct`；AI 不能覆盖程序判断。
   - B/C 都在学生提交一句回答后调用一次 `guidance_evaluate`，完成评价、错因、纠正方向和下一问题。
   - AI 分析结果和本轮对话写入现有会话记录后，才更新 `step_index` 并返回下一问题。
   - AI 失败时保留当前步骤，不返回下一问题，不自动再次调用模型。

3. 辅助函数：
   - 增加可复用的选项标签标准化逻辑，兼容 `A` 和 `A. 选项内容`。
   - 增加当前 B/C 步骤上下文组装逻辑，避免只传原题答案。
   - 保留原有 `_extract_b_mode_step`、`_extract_c_mode_step` 的数据兼容能力。

### 14.2 AI 组件任务：`apps/common/ai/components/guidance.py`

1. 扩展运行时 `GuidanceContext`，增加模式、当前步骤问题、当前步骤参考答案、关键评分点、题目选项、题目解析、视觉事实和历史回答等上下文。
2. `evaluate_student_reply` 改为返回结构化字典，而不是只返回评价字符串。
3. 使用严格的 Pydantic 响应模型解析以下字段：
   - `result`：`correct`、`partial`、`incorrect`、`unclear`。
   - `error_type`：概念错误、读图错误、计算错误、条件遗漏、表达不完整、答非所问、无法判断等。
   - `evaluation`：学生可读的简短评价。
   - `correction_direction`：针对本轮错误原因的纠正方向。
   - `next_question`：完成记录后展示的下一问题。
   - `next_hint`：辅助提示。
   - `confidence`：0 到 1 之间的置信度。
4. 继续使用 `extra="forbid"` 和统一响应解析器，模型返回非法 JSON 或缺少必填字段时按 AI 响应错误处理。
5. 不返回模型思维过程，不要求模型输出长篇解析。

### 14.3 提示词任务

调整 `guidance_evaluate` 对应提示词，使 B/C 共用一次评价调用但明确区分模式：

- B 模式输入程序判定结果、当前固定问题、选项语义、正确选项、学生选择和必要题目上下文。
- C 模式输入当前开放问题、当前步骤参考答案、关键评分点、题干、选项、解析、视觉事实、历史回答和学生本轮回答。
- 明确要求模型不能修改 B 模式程序给出的正确性结论。
- 学生只提交选项、没有解释时，错因只能表述为“可能原因”或“无法确定”，不能伪造确定的心理过程。
- 一次响应必须同时返回评价、错因、纠正方向和下一问题，不得要求服务端再次调用模型。

### 14.4 配置和 AI 客户端任务

1. `config/ai_config.cfg` 的 `guidance_evaluate` 保持 provider 为 `qwen`、model 为 `qwen3.7-flash`，调整为实时交互配置。
2. `apps/common/ai/config.py` 当前要求所有任务 `timeout_seconds = 300`，需要改为允许实时任务使用受控短超时，但不能降低离线任务的现有上限。
3. `apps/common/ai/provider_limiter.py` 当前并发租约等待默认最多 300 秒，需要为学生实时任务增加独立的 2～5 秒等待上限；不能让实时请求继续继承全局 300 秒等待。
4. `guidance_evaluate` 的自动重试设置为 0，确保每条学生回答最多一次模型调用。学生主动重新提交才视为新的一轮请求。
5. 由 `guidance_views.py` 创建的 `trace_id` 必须传入 `GuidanceContext`，并继续传递到 AI 客户端日志。
6. `guidance_generate` 可以保留为后台准备任务，但不得在学生启动 C 模式的同步接口中调用。

后台任务优先复用项目已有的 Celery 任务和调度方式（`apps/review/ai_mode_dispatch.py`、`apps/review/tasks.py`），不要在学生同步请求中直接执行题目完整生成；现有 `apps/common/management/commands/generate_ai_guidance.py` 继续作为人工/批量补数据工具，不作为学生接口的实时依赖。

### 14.5 前端任务

涉及文件：`uniapp/src/pages/student/guidance.vue`、`uniapp/src/api/student.ts`。

1. 保持现有两个接口路径和请求方法。
2. B 模式继续提交选项，但后端兼容选项标签和完整选项文本。
3. 提交按钮保持防重复点击；建议增加 `reply_id`（UUID）作为可选幂等参数。
4. 回复成功后显示 `evaluation`、`error_type` 和 `correction_direction`，再显示 `next_question` 或兼容使用现有 `next_hint`。
5. AI 失败时停留在当前步骤，显示友好提示，不显示 `AIRequestError`、`AIResponseError` 等内部异常。
6. 只有收到服务端确认已记录且允许推进的响应后，前端才更新为下一步骤。

## 15. 接口实施契约

### 15.1 启动接口

接口：`POST /api/v1/student/guidance/sessions`

请求保持兼容：

```json
{
  "mode_type": "B|C",
  "question_id": "题目 UUID"
}
```

启动接口不承担学生错因分析。成功响应继续使用现有外层结构，`data` 至少保留：

```json
{
  "session_id": "会话 UUID",
  "mode": "B|C",
  "step_index": 0,
  "total_steps": 4,
  "hint": "当前问题",
  "options": [],
  "question_info": {},
  "is_fallback": false
}
```

`options` 仅在 B 模式返回。C 模式数据缺失时使用可用兜底并标记 `is_fallback=true`，不能因为后台准备未完成就同步等待完整 AI 生成。

### 15.2 回复接口

接口：`POST /api/v1/student/guidance/sessions/{session_id}/reply`

请求：

```json
{
  "reply": "学生的一句话回答或 B 模式选项",
  "reply_id": "可选 UUID，用于幂等控制"
}
```

成功响应沿用现有外层结构，`data` 统一包含以下字段；不适用的字段返回 `null` 或空数组：

```json
{
  "mode": "B|C",
  "step_index": 1,
  "total_steps": 4,
  "is_correct": false,
  "evaluation": "你已经识别出……但还遗漏了……",
  "error_type": "表达不完整",
  "correction_direction": "先明确……再判断……",
  "next_question": "下一步问题",
  "next_hint": "兼容前端的下一步提示",
  "is_completed": false,
  "ai_status": "success"
}
```

为兼容现有前端，`next_hint` 可以继续承载下一问题；新前端优先读取 `next_question`。B 模式现有的 `correct_answer`、`analysis` 和 `options` 字段继续保留。

### 15.3 AI 失败响应

AI 失败时保持统一接口外层结构，`data` 返回：

```json
{
  "mode": "B|C",
  "step_index": 0,
  "is_completed": false,
  "evaluation": null,
  "error_type": null,
  "correction_direction": null,
  "next_question": null,
  "next_hint": null,
  "ai_status": "unavailable",
  "retryable": true
}
```

服务端保存学生回答和失败状态，但不增加 `step_index`。前端只能在学生主动重新提交后发起新请求，服务端不得自动重试或直接推进到下一问题。具体 HTTP 状态码应遵循项目统一错误协议，但无论采用业务错误码还是 HTTP 错误码，都必须携带 `trace_id`。

## 16. 数据记录和事务边界

### 16.1 不增加数据库表字段

继续使用 `apps/study/models.py` 中现有的 `AIGuidanceSession`：

- `mode_type`：当前 B/C 模式。
- `session_status`：`running`、`completed`、`downgraded` 等现有状态。
- `invalid_input_count`：现有无效输入计数。
- `content_log_json`：复用现有 `step_index`、`steps`、`answers` 保存学生对话和动态分析。

### 16.2 建议的现有 `answers` 日志项

在现有 `answers` 数组中记录本轮信息，不改变数据库表结构：

```json
{
  "step": 0,
  "mode": "B",
  "reply_id": "UUID",
  "user_answer": "A. 分析已知条件",
  "normalized_answer": "A",
  "correct_answer": "A",
  "is_correct": true,
  "evaluation": "……",
  "error_type": null,
  "correction_direction": "……",
  "next_question": "……",
  "ai_status": "success",
  "trace_id": "……",
  "latency_ms": 3200
}
```

字段属于会话 JSON 的运行时日志，不是题目引导数据结构。B 模式若只提交选项，则 `user_answer` 和 `normalized_answer` 均应保留，便于后续审计。

### 16.3 单次调用和幂等处理顺序

建议使用现有会话记录实现幂等，不增加数据库字段：

1. 校验会话归属、状态和回答非空。
2. 在事务中锁定会话，读取当前 `step_index`，根据 `reply_id` 或“步骤 + 回答”的哈希检查是否已处理。
3. 写入一条 `pending` 的现有 `answers` 日志项后提交事务，防止同一回答并发重复调用。
4. 在事务外调用一次 `qwen3.7-flash`，避免长时间持有数据库锁。
5. 再次锁定会话，确认该日志项仍为当前请求；成功则写入 AI 结果、更新 `step_index`，失败则写入失败状态但保留原步骤。
6. 若请求重复到达，直接返回已记录结果，不再调用模型。

如果服务进程在 `pending` 状态中断，应由超时清理任务将其标记为失败，不能永久阻塞该会话。

## 17. B/C 单轮处理流程

### 17.1 B 模式

```text
读取当前 B 步骤
    ↓
标准化 A/B/C/D 标签
    ↓
程序确定 is_correct
    ↓
调用一次 qwen3.7-flash
    ↓
AI 分析本轮回答、动态错因和纠正方向
    ↓
写入 answers 现有日志
    ↓
返回下一问题/固定下一步骤
```

程序确定的 `is_correct` 是最终正确性；模型只负责面向学生的解释、动态错因和纠正方向。B 模式只有选项回答时，模型对错因的判断证据有限，必须允许返回“无法确定”，不能声称已经准确知道学生的真实思维过程。

### 17.2 C 模式

```text
读取当前 C 步骤和题目上下文
    ↓
接收学生一句自然语言回答
    ↓
调用一次 qwen3.7-flash
    ↓
同时返回评价、错因、纠正方向和下一问题
    ↓
写入 answers 现有日志
    ↓
返回下一问题
```

“一轮”指一次学生回答对应一次模型调用；学生可以继续回答服务端返回的下一问题，但同一条回答不再进行评价调用、追问调用、总结调用等多轮 AI 串联。

## 18. 具体模型输入和输出要求

### 18.1 模型输入最小集合

B/C 实时评价请求至少包含：

- `mode`。
- 原题题干、题型、选项和解析（可按 Token 限制裁剪）。
- 当前引导问题。
- 当前步骤参考答案和关键评分点。
- 图像结构化事实；没有视觉事实时明确告知模型不可从文本推断图像细节。
- 历史回答摘要。
- 学生本轮回答。
- B 模式程序计算出的 `is_correct`。

不得只传原题答案 `BD` 作为当前步骤参考答案，也不得把前端展示图片的 URL 当作模型已经看到了图片。

### 18.2 模型输出约束

提示词应要求：

1. `evaluation` 不超过约定长度，直接面向学生。
2. `correction_direction` 只指出下一步纠正方向，不直接泄露整道题答案。
3. `next_question` 必须围绕本轮错因或下一个知识点。
4. 正确回答的 `error_type` 返回 `null` 或“无明显错误”。
5. 证据不足时 `result=unclear`，不编造错因。
6. 不输出 Markdown、思维过程或额外字段，便于严格 JSON 解析。

## 19. 性能、异常和可观测性实施值

### 19.1 实时配置

| 项目 | 实施值 |
| --- | --- |
| provider/model | `qwen` / `qwen3.7-flash` |
| temperature | `0.1` |
| max_tokens | `1024` |
| timeout_seconds | `10` 秒，允许范围 8～15 秒 |
| retry_count | `0` |
| provider lease wait | `3` 秒，允许范围 2～5 秒 |
| response_format | `json` |
| enable_thinking | 关闭 |

`guidance_generate` 仅用于后台准备，可以保留较长超时和重试；不能把它与学生回答后的实时 `guidance_evaluate` 混用。

### 19.2 错误分类

统一记录：配置错误、网络错误、请求超时、429 限流、5xx、并发租约超时、响应 JSON/Schema 错误、题目上下文缺失、会话状态冲突和重复请求。

每次学生回答至少记录 `session_id`、`question_id`、`mode`、`step_index`、`reply_id`、`trace_id`、实际 provider/model、请求耗时、重试次数、AI 状态和是否推进步骤。

### 19.3 性能验收

- 启动接口不再等待同步 `guidance_generate`。
- 正常 AI 回复 P95 目标不超过 8 秒，P99 不超过 15 秒。
- 并发资源不足时最多等待 3～5 秒后返回可理解的失败状态。
- 单条学生回答的模型调用计数为 1，自动重试计数为 0。
- AI 失败时接口不会把请求拖到 300 秒，也不会错误推进步骤。

## 20. 开发测试清单

### 20.1 后端单元测试

在现有 `apps/study/tests/test_guidance_ai.py` 基础上补充：

1. B 模式提交 `A`、`A. 选项内容` 均能得到相同 `is_correct`。
2. B 模式每次回答只调用一次 `guidance_evaluate`，并把结果写入现有 `answers`。
3. B 模式程序判断为正确时，模型不能覆盖 `is_correct`。
4. B 模式只提交选项时，模型可以返回“无法确定”错因，不产生确定性臆测。
5. C 模式模型上下文包含当前问题、当前参考答案、关键点、历史回答和视觉事实。
6. C 模式一次模型响应同时返回评价、错因、纠正方向和下一问题。
7. AI 返回非法 JSON、超时、限流或配置错误时，不自动重试、不增加 `step_index`。
8. AI 失败后当前回答和失败状态仍被记录，前端不会收到内部异常名称。
9. C 模式缺少 `ai_answer_c` 时，启动接口不调用同步 `generate`，能够返回可用兜底。
10. C 降级到 B 时 `mode_type`、`session_status`、`step_index` 和当前步骤一致。
11. 相同 `reply_id` 或相同步骤和回答重复提交时只产生一次 AI 调用和一条有效记录。

### 20.2 接口和前端联调

使用示例题目验证：

- C 模式首屏能展示问题，不等待数分钟。
- 学生回答“匀速运动”时，模型能结合当前“斜率代表什么”的问题判断为部分回答或表达不完整，而不是拿原题答案 `BD` 直接比较。
- 返回中先出现评价、错因和纠正方向，再显示下一问题。
- AI 失败时页面停留当前步骤，点击或主动重新提交才产生新请求。
- B 模式选择完整文本和标签均能正确推进。

### 20.3 模型质量测试

建立覆盖物理、数学、图像题、计算题、概念题的真实样本集，由教师标注：

- 回答结果分类是否正确。
- 错因分类是否合理。
- 纠正方向是否能帮助学生继续作答。
- 下一问题是否针对当前错误。
- 学生完成引导后的原题重答正确率。

### 20.4 建议验证命令

后端改造完成后，至少执行：

```bash
pytest apps/study/tests/test_guidance_ai.py
pytest apps/common/ai/tests/test_config.py apps/common/ai/tests/test_prompt_registry.py
```

如果项目 CI 使用 Django test runner，则按现有 CI 命令执行同等测试集合；前端按项目现有 lint、类型检查和构建命令执行，不新增独立的构建方式。

## 21. 实施顺序、上线和回滚

### 21.1 开发顺序

本节是第 11 节阶段门禁的执行索引。开发必须按“阶段 0 → 阶段 1 → 阶段 2 → 阶段 3 → 阶段 4 → 阶段 5 → 阶段 6”顺序进行；下列任务完成后，必须先完成对应阶段的六类验证并留存记录，才允许开始下一阶段。

1. 先补充 AI 结构化响应和提示词测试，不接入页面。
2. 修复 B 选项标签标准化和现有会话日志写入。
3. 改造 C 上下文传递和单次回复处理。
4. 增加事务、幂等和失败不推进逻辑。
5. 调整实时配置、并发等待和 trace_id 传递。
6. 更新前端显示评价、错因、纠正方向和失败状态。
7. 完成单元测试、接口联调和模型质量测试。

### 21.2 灰度上线

1. 阶段 0～5 只能在开发或测试环境完成阶段性灰度，不得直接影响全量学生。
2. 阶段 6 先在测试环境使用固定样本验证 B/C 两种模式。
3. 测试环境六类指标全部通过后，小比例学生开启新回复链路，记录耗时、失败率、重复请求和错因质量。
4. 灰度指标达标后逐步放量，持续观察实时任务 P95/P99、AI 不可用率和学生重答正确率。
5. 稳定并完成最终门禁确认后，再关闭旧的同步 C 生成路径。

### 21.3 回滚方式

回滚优先通过配置或功能开关停用新的实时评价链路，保留已有 B/C 静态步骤和会话日志，不执行数据库回滚。若模型服务异常，B 模式保留程序正确性判断，C 模式返回静态当前步骤提示并停止推进。

每个阶段的灰度验证失败，都应回滚到该阶段开始前的稳定版本，修复完成并重新通过六类门禁后，才能继续后续阶段。

## 22. 实施完成判定

只有同时满足以下条件，才可以认为方案已从技术建议变为可上线实施方案：

1. 开发任务已经对应到 `guidance_views.py`、`guidance.py`、AI 配置、前端页面和测试文件。
2. B/C 请求和响应字段已按现有 API 外层协议确定。
3. 未新增数据库表字段，动态错因明确写入现有学生会话记录。
4. 每条学生回答只触发一次 `qwen3.7-flash`，不自动重试、不串联第二次模型调用。
5. AI 结果写入成功后才推进步骤，失败时保留当前步骤。
6. B 模式程序判定和 AI 错因分析职责分离，C 模式传入当前步骤完整上下文。
7. 测试覆盖正确性、响应失败、重复提交、降级、图像事实和前端展示。
8. 性能指标和灰度回滚方式已经在测试环境验证。

因此，本文件现在可作为开发任务拆分、接口评审、测试编写和灰度上线的实施依据；在实际开发前只需要完成接口字段评审、错误码确认和产品文案确认，不需要重新进行方案选型。
