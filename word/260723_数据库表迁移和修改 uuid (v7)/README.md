## ⚠️ 重要：执行顺序

### 正确的执行顺序

```
1️⃣ 先执行 UUID v7 迁移
   └─> 所有新表直接使用 UUID v7 结构
   
2️⃣ 再执行缺失表迁移
   └─> 迁移的表也是 UUID v7 结构
```

### ❌ 错误的执行顺序

```
❌ 先迁移缺失表（int ID）
   └─> 再改 UUID v7（需要再次迁移数据）
   
❌ 会导致两次数据迁移，风险加倍
```

---

## 🎯 推荐执行路径

### 方案 A：完整迁移（推荐）

适用于：生产环境，需要彻底改造

**步骤**：
1. 阅读 **02_UUID_v7_完整迁移方案.md**
2. 本地修改代码（UUID v7）
3. 本地测试通过
4. 服务器执行 UUID v7 迁移
5. 验证功能正常
6. 阅读 **01_缺失表迁移方案.md**
7. 执行缺失表迁移（新表直接是 UUID v7）
8. 全面验证

**优点**：
- 新表直接使用 UUID v7，避免重复迁移
- 一次到位，风险最小

---

适用于：紧急修复 500 问题，暂缓 UUID v7 改造

1. 只执行 **01_缺失表迁移方案.md** 的 P0 优先级
2. 修复 `knowledge_points` 表（解决 500）
3. 其他功能正常后，再规划 UUID v7 迁移

**优点**：
- 快速修复问题
