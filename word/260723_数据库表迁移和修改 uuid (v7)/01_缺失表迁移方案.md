> **执行顺序**：本文档应在 UUID v7 迁移**之后**执行（新表直接使用 UUID v7 结构）

## 🎯 执行方案

### 方案选择

根据**实际需求**选择以下方案之一：

#### 方案 A：Django 迁移创建（推荐）

适用于：表有对应的 Django 模型定义（`knowledge_points`, `learning_mission` 等）

**优点**：
- 由 Django 管理，与代码一致
- 自动处理 UUID v7 主键
- 支持后续迁移

**步骤**：
1. 修改模型 `managed=False` → `managed=True`
2. 执行 `python manage.py migrate`
3. Django 自动创建表结构（UUID v7）

#### 方案 B：手动执行 SQL 创建

适用于：Django 模型中不存在的表（系统表、日志表等）

**优点**：
- 直接控制表结构
- 不依赖代码迁移

**步骤**：
1. 从 `public.sql` 提取建表语句
2. 修改 `id` 字段类型：`int8` → `UUID`
3. 在服务器执行 SQL

## ⚠️ 重要注意事项

### 关于 `managed = False` 的模型

`knowledge_points` 模型当前使用 `managed = False`，意味着：
- Django 不会自动创建/修改这个表
- 必须手动维护表结构

**建议**：
- 如果这个表由 Django 管理：改为 `managed = True`
- 如果是外部系统维护：保持 `managed = False`，手动导入表结构

---

### 表结构差异

旧库（qisi_ai_tutor）与新库（appdb）的表结构可能存在差异：
- 字段类型
- 约束条件
- 索引定义

**建议**：
- 优先使用 Django 模型定义（确保代码一致）
- 如需使用旧库结构，手动比对字段差异

---

### 外键关系

迁移表时要注意外键关系：
- `learning_mission.creator_teacher_id_id` → `user_account.id`
- `learning_mission.class_id` → `institutions.class.id`
- 等等

**UUID v7 迁移后，外键字段类型也要改为 `UUIDField`**（见 UUID v7 迁移文档）
