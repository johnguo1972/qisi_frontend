# 本地未提交代码与远程分支安全合并通用方案

## 1. 适用场景

适用于本地分支落后远程分支较多、工作区存在大量未提交修改，同时需要将远程 `main` 更新合并到本地，但暂时不能提交本地代码的场景。

目标是：远程代码更新到本地、本地修改完整保留、冲突逐文件合并、验证代码可运行，最后保持本地修改未提交。

本方案不直接执行 `git pull`，不使用 `git reset --hard`，不覆盖 `.env`，不自动提交或推送。

## 2. 操作前约束

1. 先确认当前目录、当前分支和工作区状态。
2. `.env`、数据库备份、媒体备份等本地文件必须单独保护；不要使用 `git stash -u`，避免把忽略文件或大体积备份纳入暂存。
3. 所有本地修改属于用户资产，不能通过整文件覆盖远程版本来解决冲突。
4. 远程更新完成后，必须检查代码冲突、测试、构建和关键接口；验证完成前不删除保护分支、补丁或 stash。

## 3. 第一阶段：比较本地与远程

### 3.1 保存基线

```powershell
git status --short
git branch --show-current
git rev-parse HEAD
git log --oneline --decorate -10
git remote -v
```

### 3.2 获取远程提交信息

```powershell
git fetch --no-tags origin main
git rev-parse origin/main
git rev-list --left-right --count HEAD...origin/main
git log --oneline HEAD..origin/main
git diff --stat HEAD origin/main
```

如果远程仓库不可访问，可使用 `git ls-remote origin refs/heads/main` 检查远程真实提交；不要仅依据本地过期的 `origin/main` 判断远程是否最新。

### 3.3 找出文件交集

```powershell
git diff --name-only HEAD origin/main
git diff --name-only
git diff --name-only --diff-filter=U
```

将“本地已修改文件”和“远程本次变更文件”逐项比较。文件同时改动不一定是功能冲突，需要继续查看具体代码区域和功能边界。

## 4. 第二阶段：保护本地修改

### 4.1 创建外部补丁保护

补丁目录建议放在仓库外，例如：

```powershell
$backup = 'D:\path\local-merge-protection\yyyyMMdd'
New-Item -ItemType Directory -Force $backup | Out-Null
git status --short | Out-File "$backup\status-before.txt" -Encoding utf8
git diff --binary HEAD | Out-File "$backup\local-tracked-changes.patch" -Encoding utf8
git diff --stat HEAD | Out-File "$backup\tracked-diff-stat.txt" -Encoding utf8
```

数据库、媒体包、`.env` 等未跟踪或被忽略文件，应记录路径并使用文件系统备份；不要依赖 Git 补丁恢复它们。

### 4.2 建立临时集成分支

```powershell
git switch -c integration/remote-main-local-merge-yyyyMMdd
```

该分支只用于集成和验证，不要在验证完成前删除。

### 4.3 暂存本地已跟踪修改

```powershell
git stash push -m 'local-before-remote-merge-yyyyMMdd'
```

这里不加 `-u`，这样可以避免误处理 `.env` 和大文件备份。未跟踪文件仍留在工作区，必须通过前面的外部备份保护。

## 5. 第三阶段：更新远程代码

```powershell
git fetch --no-tags origin main
git merge --ff-only origin/main
```

如果当前本地没有已提交但未推送的提交，优先使用 `--ff-only`，只把临时集成分支快进到远程最新提交，不制造无意义的合并提交。

如果本地存在自己的提交，不能强行快进，应在临时集成分支中经过确认后使用普通 merge 或 rebase；仍然不能直接改写用户原分支。

确认：

```powershell
git rev-parse HEAD
git rev-parse origin/main
```

两者一致，表示临时集成分支已经包含远程 `main` 当前代码。

## 6. 第四阶段：恢复本地修改并处理冲突

```powershell
git stash pop
git status --short
git diff --name-only --diff-filter=U
```

### 6.1 冲突处理原则

每个冲突文件按以下顺序处理：

1. 查看 `<<<<<<<`、`=======`、`>>>>>>>` 两侧代码以及所在函数的完整上下文。
2. 明确远程新增功能和本地新增功能分别是什么。
3. 保留双方互不冲突的功能；同一函数内也应尽量合并参数、分支和错误处理，而不是选择整块的某一侧。
4. 关注接口参数、返回结构、权限判断、环境配置、前端平台条件编译和异常提示，避免只解决语法冲突而丢失功能。
5. 处理完成后检查目标文件不再有冲突标记，再执行 `git add <file>` 标记该文件已解决。

示例：

```powershell
rg -n '^(<<<<<<<|=======|>>>>>>>)' <冲突文件>
git add <已解决文件>
```

### 6.2 `.env` 的处理

`.env` 是部署环境机密配置，不应通过远程代码覆盖。远程仓库只应维护 `.env.example` 或配置说明；本地和服务器 `.env` 应分别备份、人工比较和更新。

## 7. 第五阶段：验证

### 7.1 Git 与 Python 基础检查

```powershell
git diff --check
git diff --cached --check
python manage.py check
```

### 7.2 后端测试

先运行受影响模块和新增功能测试，再运行全量测试：

```powershell
python -m pytest apps/accounts/tests apps/qrcode/tests.py apps/practice/tests -q
python -m pytest <远程新增测试文件> -q
python -m pytest -q
```

如果全量测试因本机工具链失败，应区分“代码失败”和“环境失败”，记录具体命令、版本和错误；不能把环境错误当成代码验证通过。

### 7.3 前端构建

在 `uniapp` 目录执行：

```powershell
npm run build:h5
npm run build:mp-weixin
npm run build:app
```

构建成功后，再使用对应开发工具验证登录、角色切换、核心页面和涉及的接口。警告需要记录；只有确认不影响运行时，才能作为非阻断项保留。

## 8. 第六阶段：保持未提交状态并交付

如果只是为了标记冲突而暂时 `git add`，验证后可安全取消暂存：

```powershell
git restore --staged -- .
git status --short
```

该命令只取消暂存，不丢弃工作区内容。不要执行 `git reset --hard`。

交付前确认：

```powershell
git branch --show-current
git rev-parse HEAD
git rev-parse origin/main
git diff --name-only
git diff --name-only --diff-filter=U
git stash list -n 3
```

应满足：

- 当前仍在临时集成分支；
- `HEAD` 与 `origin/main` 一致；
- 没有未解决冲突；
- 本地修改仍显示为未提交；
- 保护补丁和 stash 仍保留；
- 没有执行 commit、push 或部署。

本地未提交文件数量原则上应保持不变；如果按要求新增了方案文档，该文档本身会额外产生一个未提交文件，这是预期结果，应单独说明。

## 9. 回滚与异常处理

- `git stash pop` 发生冲突时，stash 通常会保留；不要立即删除 stash。
- 普通 merge 尚未完成时可使用 `git merge --abort`，但不要在工作区状态不清楚时执行破坏性命令。
- 如果发现合并方向错误，先保留当前状态、补丁和 stash，再人工确认回退方案。
- 任何涉及数据库、`.env`、媒体文件或服务器的操作，都应使用单独备份和明确授权，不能通过 Git 合并自动处理。
