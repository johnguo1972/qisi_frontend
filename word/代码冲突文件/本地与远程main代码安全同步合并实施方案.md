# 本地与远程 main 代码安全同步合并实施方案

> 当前适用基线：2026-08-30。执行前必须重新读取远程实时引用；本文中的提交号是本次检查得到的基线，不是永久固定值。

## 1. 文档目的

本文用于处理以下场景：

- 本地实际开发分支不是 `main`，而是 `integration/remote-main-local-merge-20260826`；
- 本地工作区存在大量未提交代码、文档、备份和配置文件；
- 远程 `main` 在本地当前开发分支基础上又新增了 23 个提交；
- 需要以远程实时最新 `main` 为基础整合本地 103 个未提交路径中的有效开发成果；
- 需要解决代码文件和 Django 数据库迁移冲突；
- 合并后切换本地工作分支为 `main`；
- 前后端、迁移、数据库和运行状态均通过验证后，形成供人工核对的本地整合结果。

本文只规定本地拉取和合并方案，不代表已经执行任何拉取、合并、提交或推送操作。
本方案的执行终点是本地完成远程 `main` 同步、冲突处理、切换本地 `main` 和验证；不包含将本地代码提交或推送到远程 `main`。

## 2. 必须先明确的 Git 规则

### 2.1 未跟踪文件的含义

Git 显示的“未跟踪文件”表示文件不在当前分支的提交和暂存区中。它们可能是：

- 本地新建但从未提交的代码；
- 本地开发过程中新增的迁移、页面、测试和文档；
- 备份文件、压缩包、配置文件；
- 曾在其他分支存在，但当前分支没有纳入版本管理的文件。

未跟踪不等于文件错误，也不等于任何远程分支都没有该文件；它只说明当前工作区不会由 Git 自动合并或推送该文件。

### 2.2 “保留未提交文件”和“直接 push”不能同时成立

`git push` 只推送提交，不推送未提交或未跟踪文件。因此：

- 在合并检查阶段，可以保留当前未提交路径处于未提交状态，用于人工确认；本次检查为 103 个路径；
- 如果未来另行授权推送，需要将应该进入远程仓库的代码、迁移、测试和文档分批提交；
- 数据库备份、媒体备份、`.env.old`、`.claude` 等不应提交的文件可以继续保持未跟踪；
- 如果要求推送后仍然显示全部未提交路径，则这些文件不会进入远程仓库，这与“将本地代码 push 到远程 main”相矛盾。

本方案将“未提交路径仍可见”定义为合并后的审核阶段目标，不定义为推送完成后的工作区目标。执行时必须以 `git status --porcelain=v1 -uall` 的实际结果为准，不固定要求数量为 101、102 或 103。

### 2.3 冲突判定和远程保护规则

必须先判断冲突是否属于同一功能，不能仅因为文件路径相同就覆盖本地代码。

| 判断结果 | 处理方式 |
|---|---|
| 同一文件、同一功能、同一业务逻辑冲突 | 以远程 `main` 为准，本地对应实现不覆盖远程实现 |
| 同一文件、不同功能、代码位置不同 | 两个功能都保留，合并后检查导入、命名、调用关系和语义 |
| 同一文件、不同功能但共享模型、函数或配置 | 两个功能原则上都保留，统一公共部分，避免重复定义和行为覆盖 |
| 同一文件、无法确认是否同一功能 | 暂停自动处理，先确认功能归属和调用链 |

“以远程仓库为准”仅适用于同一功能的代码冲突，不表示远程文件一旦与本地同名就整体覆盖本地文件。

远程仓库保护要求：

- 不执行 `git push`；
- 不创建或更新远程合并请求；
- 不执行强制推送；
- 不修改远程分支、远程提交和远程迁移文件；
- 所有冲突处理只发生在本地临时整合分支或本地 `main`；
- 合并完成后只供本地核对，待用户确认后再决定是否提交远程。

## 5. 总体执行顺序

必须严格按以下顺序执行：

1. 停止开发操作，冻结工作区。
2. 读取分支、提交、远程实时版本和未提交文件清单。
3. 区分应保留代码、应保留文档、应保留备份和禁止提交文件。
4. 备份本地工作区和数据库。
5. 在当前开发分支上创建本地安全备份分支。
6. 保存本地代码成果，避免直接在脏工作区切换分支。
7. 获取远程最新 `main` 引用；此步骤只在正式执行阶段进行。
8. 以远程最新 `main` 创建新的整合分支。
9. 将本地安全分支合并到整合分支。
10. 以远程版本为准处理确认的冲突文件。
11. 处理 Django 迁移编号和依赖冲突。
12. 检查冲突标记、导入错误、模型错误和路由错误。
13. 执行数据库迁移检查和实际迁移验证。
14. 执行后端测试、前端构建和前后端运行验证。
15. 在审核阶段确认本地 103 个路径的去留。
16. 在本地整合分支完成核对，不向远程提交或推送。
17. 仅在本地确认整合结果后切换本地工作分支为 `main`。
18. 确认本地 `main` 已包含执行当天远程最新代码和本地合并结果。
19. 再次执行完整检查。
20. 停止在本地核对结果，不执行远程 `main` 提交和推送。

## 6. 阶段一：冻结和盘点工作区

### 6.1 不得直接执行的操作

在完成备份和确认前，禁止执行：

- `git pull`；
- `git reset --hard`；
- `git clean -fd` 或 `git clean -fdx`；
- 直接切换到本地 `main`；
- 直接删除未跟踪迁移、代码或备份；
- 使用 `git pull -X theirs` 试图自动覆盖全部冲突。

### 6.2 盘点内容

执行时记录以下信息：

- 当前分支和 `HEAD`；
- 本地 `main` 的提交；
- 远程实时 `main` 的提交；
- 当前分支与远程 `main` 的提交数量差异；
- 已修改文件清单；
- 未跟踪文件清单；
- 已忽略文件清单；
- 本地数据库迁移执行状态；
- 当前 Python、Node、npm 版本。

未提交文件必须按照以下类别登记：

| 类别 | 处理原则 |
|---|---|
| 本地业务代码 | 需要代码评审，符合要求后提交 |
| 本地迁移文件 | 必须与远程迁移链统一后再提交 |
| 测试文件 | 通过测试后提交 |
| 方案文档 | 确认内容后提交 |
| `.env.old`、密钥、个人配置 | 不提交，单独备份 |
| `.claude` 等本地工具目录 | 默认不提交，除非项目明确需要 |
| SQL、tar.gz、媒体备份 | 不提交到代码仓库，保留在备份位置 |

## 9. 阶段四：以远程最新 main 创建整合分支

正式执行时，先获取远程 `main` 的最新引用，然后从远程最新 `main` 创建整合分支，例如：

```text

```

整合分支的基线必须是执行当天远程实时 `main` 的最新哈希。本次检查的基线为 `f62578a2`，而不是：

- 本地旧 `main` 的 `b202fbb3`；
- 本地缓存的 `origin/main` 的 `aee0a959`。

随后将本地安全分支合并到该整合分支。合并过程必须保留合并记录，不能通过强制覆盖隐藏冲突。

## 10. 阶段五：冲突处理规则

### 10.1 冲突优先级和处理边界

本次明确采用以下优先级：

1. 远程最新 `main` 的同路径代码优先；
2. 本地没有冲突的新增功能保留；
3. 同一文件但功能不同的本地和远程实现都保留，按功能边界合并；
4. 同一功能两边都修改时，以远程实现为准，不直接拼接未经验证的代码；
5. 迁移必须以远程迁移链为基础重新整理，但不同功能的迁移不能无记录删除；
6. 任何被远程同功能实现覆盖的本地功能，必须记录在合并说明中；
7. 合并后必须检查重复类、重复路由、循环导入、变量遮蔽、迁移分叉和语义改变。

## 14. 阶段九：仅本地合并、切换 main 和核对

### 14.1 本地保存原则

为了保护本地成果，可以创建本地安全分支或本地临时保护提交，但这些内容只存在本地，不得推送远程。

本阶段禁止执行：

- 向远程 `main` 提交；
- 向远程 `main` 推送；
- 创建或更新远程合并请求；
- 强制推送或修改远程历史。

本地审核阶段可以保留未提交工作区，也可以使用本地临时提交保护文件；两种方式都不会修改远程仓库。

如果采用本地临时提交，提交内容仍按功能分组：

- 远程 main 同步和冲突处理；
- 本地 P1/P2/P4 业务代码；
- 数据库迁移；
- 前端页面和 API；
- 测试；
- 文档。

备份、密钥和个人配置不得进入提交。

### 14.2 切换本地 main

整合分支验证通过后，再将本地 `main` 更新到已验证的整合结果。切换前再次确认：

- 工作区不存在未保存的代码；
- 备份已完成；
- 整合分支测试通过；
- 本地 `main` 不包含需要保留的旧内容。

切换完成后检查：

- `HEAD` 位于本地 `main`；
- 本地 `main` 包含远程最新 `main`；
- 本地 `main` 包含已经核对的本地合并功能；
- 远程冲突文件已按方案处理。

### 14.3 本地核对结束条件

本方案不包含推送。合并后必须确认：

- 本地 `main` 已包含远程实时 `main`；
- `git diff <执行当天远程main哈希>...main` 内容符合预期；不能使用未更新的 `origin/main` 缓存值代替；
- 数据库迁移文件和模型一致；
- 前后端测试和构建已通过；
- 不包含 SQL、tar.gz、`.env.old`、密钥和个人目录；
- 远程仓库没有产生任何新提交、分支变化或文件变化；
- 将核对结果和待后续提交清单交由用户确认。

后续是否提交和推送，必须另行获得明确授权，不属于本文档执行范围。
