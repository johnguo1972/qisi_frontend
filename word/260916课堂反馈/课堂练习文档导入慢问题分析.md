# 课堂练习文档导入慢问题分析

## 1. 文档信息

- 分析日期：2026-09-16
- 分析范围：课堂练习页面“导入课堂练习题”对应的 PDF/Word 文档导入链路
- 关联接口：`/api/v1/courses/{course_id}/questions/import-document/{task_id}/status/`
- 示例任务：`01a0aa78-2f51-7a22-af04-ac3bf155301f`
- 示例文件：`word/260915练习题错题精练/2026年秋季物理9年级A%2B班-练习册（上册）(1).docx`
- 本次处理边界：本文只记录原因和后续建议；本轮只优化导入历史弹窗错误信息，没有修改导入并发、超时、重试、队列或断点续传逻辑。

## 2. 现象与结论

### 2.1 现象

生产环境导入一个约 19 MB 的 DOCX 后，前端持续轮询状态接口近 3 小时，任务长期处于 `structuring`。截图显示任务在结构化阶段约 46%，同时出现“AI response is not valid JSON”和“AI provider request timed out”等失败信息。

### 2.2 结论

文件大小不是当前耗时的主要原因。当前实现会先提取文档，再按题目逐题串行调用 AI 做结构化；318 个题目候选需要等待 318 轮 AI 请求，每一轮还可能包含重试。因此整体耗时达到小时级是代码执行模型可以解释的结果。

主要原因按优先级排列：

1. **逐题串行调用 AI**：单个 Celery 任务内使用普通 `for` 循环处理所有候选题，上一题结束后才处理下一题。
2. **单次请求超时时间较长且存在重试**：文档结构化配置的请求超时为 300 秒，`structure_candidate` 对 AI 响应错误、请求错误和资源错误最多再尝试一次；异常题目可能占用较长时间。
3. **所有题目结构化完成后才统一入库**：中途已成功的题目只保存在当前进程的 `valid` 列表中，任务重启或 worker 异常时，已完成结果不会作为题目级断点保留下来。
4. **队列配置需要核对**：代码将任务路由到 `document.import` 队列，而部署指南中的 worker 示例只监听 `celery,ai.batch`。如果生产实际使用该命令，任务会排队；但本次截图已经进入 `structuring`，说明该任务当前确实被某个 worker 消费，队列问题仍需在生产部署上确认。

## 3. 代码证据

### 3.1 前端轮询不是耗时根因

文件：`uniapp/src/pages/teacher/course-practice.vue`

- `pollCourseDocumentImport` 调用状态接口。
- 轮询间隔约 3 秒。
- 只有任务进入 `success`、`partial_success` 或 `failed` 才停止轮询。
- 在 `structuring` 阶段，前端只是等待后端任务完成，不会主动触发新的 AI 处理。

因此，反复看到同一个 status 请求是页面的正常进度查询行为，不是每次查询都重新导入文档，也不是前端重复发起 AI 请求。

### 3.2 后端处理链路是一个长串行任务

文件：`apps/study/document_import_tasks.py`

当前流程为：

```text
提取 PDF/DOCX
  -> 遍历 extracted.fragments
  -> 处理题目资源
  -> structure_candidate（逐题 AI 调用）
  -> 全部候选处理完
  -> ingest_structured_questions 统一入库
  -> 更新 success/partial_success/failed
```

关键点：

- 每个候选题都执行 `_materialize_candidate_assets` 和 `structure_candidate`。
- `valid` 和 `failures` 是当前任务函数内存中的列表。
- 只有所有候选题循环结束，才进入 `ingest_structured_questions`。
- 进度 20% 到 65% 是按逐题循环的索引计算的；截图中的 `structuring (46%)` 表示任务仍在逐题等待 AI 结果。

### 3.3 本地文件验证结果

对当前工作区中的同名 DOCX 进行只读提取验证：

- 文件大小：9,741,681 bytes（生产截图中用户反馈约 19 MB，大小存在环境差异）。
- 提取页数：373 个等效页面/分页单元。
- 提取题目候选：318 个 fragments。
- 截图显示：新增 292、跳过 24、失败 2，合计 318。

这说明导入任务实际处理的是数百个候选题，而不是只处理一个 19 MB 文件。DOCX 解压和文本提取只是前置步骤，最耗时的是后续数百次 AI 结构化请求。

### 3.4 AI 配置与重试

文件：`apps/study/document_structure_ai.py`、`config/ai_config.cfg`、`apps/common/ai/client.py`

- 文档题目结构化使用 `qwen3.7-plus`，不是课堂反馈使用的 `qwen3.7-flash`。
- 文档结构化配置 `max_tokens=8192`。
- 文档结构化配置 `timeout_seconds=300`。
- AI 客户端在当前配置下单次调用自身重试次数为 0，但 `structure_candidate` 对可重试异常再次调用，最多形成两次请求。
- 响应必须是 JSON；解析失败会抛出 `AIResponseError`，超时会抛出 `AIRequestError`。

### 3.5 截图中错误文字的来源

- `apps/common/ai/response_parser.py` 在 JSON 解析失败时生成 `AI response is not valid JSON; preview=...`。
- `apps/common/ai/client.py` 在请求超时时生成 `AI provider request timed out`。
- 旧实现把异常原文拼入 `error_summary`，前端历史弹窗直接展示，因此会看到 JSON preview、英文诊断和不可读内容。

本轮已经将弹窗展示改为安全、短文本，例如：

```text
第12题：AI响应超时
第18题：AI返回格式错误
```

这只改变错误信息的记录/展示方式，不改变导入任务的处理速度和失败重试策略。

## 4. 粗略耗时估算

若 318 道题每题平均耗时 30 秒，纯串行结构化约需 159 分钟；若平均 40 秒，约需 212 分钟。若部分题目触发 300 秒超时并重试，最坏情况会进一步拉长。因此“近 3 小时”与当前实现的串行调用方式基本吻合。

以上是基于代码和本地同名文件规模的估算，不代表生产每个请求的实际耗时。当前工作区没有生产任务 ID 对应的数据库记录和 worker 日志，生产精确耗时仍需在服务器上按 task_id 检索日志确认。

## 5. 下一阶段建议（本轮未实施）

后续讨论导入慢问题时，建议按以下顺序改造：

1. 将逐题结构化拆成可恢复的题目级任务，使用有限并发，避免单个大任务串行等待。
2. 为每道题持久化 `pending/running/success/failed`、错误类型、重试次数和结构化结果，支持断点续传和失败题单独重试。
3. 为文档结构化设置独立、合理的请求超时和重试退避策略，避免每题固定等待过长。
4. 校验生产 worker 是否监听 `document.import`，并增加队列积压、任务开始时间、当前题号和耗时日志。
5. 前端展示“已处理题数/总题数、当前题号、预计状态”，并对长期无心跳任务给出明确提示。
6. 继续保留错误脱敏：前端不展示 AI 原始响应、prompt、路径或密钥；详细诊断只写服务端日志。

## 6. 本轮变更与验证范围

本轮只涉及导入历史弹窗的错误可读性：

- 新增前端错误格式化工具，统一提取题号并映射超时、JSON 格式错误、配置错误和资源错误。
- 历史弹窗不再直接显示原始 AI response preview。
- 后端新产生的文档题目失败信息带上题号和短错误标签。
- 对旧历史数据兼容：能从旧的 JSON preview 中提取 `question_no`；无法识别题号时只显示错误类别。
- 未修改文档导入的 AI 模型、请求超时、重试、任务队列、并发和入库时机。
