# 课堂练习及错题练习题导入慢问题修复优化方案

## 1. 文档信息

- 编制日期：2026-09-16
- 适用范围：教师端课堂练习 PDF/DOCX 导入、课堂错题统计中的错题练习题 DOCX 导入
- 关联分析：[课堂练习文档导入慢问题分析.md](./课堂练习文档导入慢问题分析.md)
- 修复边界：本方案只新增和调整导入处理架构、任务状态、AI 调用策略、队列和可观测性；不改变题目去重、题目内容、错题映射和权限规则
- 实施目标：在保证导入结果正确、可恢复和可追踪的前提下，解决数百道题文档导入达到小时级的问题

## 2. 最终结论

当前问题可以通过架构优化解决，主要瓶颈不是文档大小，而是每道题单独调用 AI 并在一个 Celery 任务中串行等待。

课堂练习导入和错题练习题导入使用同一套文档 AI 结构化链路，因此两者存在同样的慢问题。错题精练生成阶段不再调用文档结构化 AI，属于另一个需要单独优化的批量数据库/PDF 任务。

本方案补齐下文的任务持久化、资源生命周期、幂等、入库上下文和调度恢复要求后，导入任务将从：

```text
一个长任务 → 逐题串行 AI → 全部完成后入库
```

调整为：

```text
父任务提取文档
  → 创建题目级任务记录
  → 有限并发调用 AI
  → 每题完成立即持久化
  → 分批入库和汇总
  → 支持失败题重试、任务恢复和部分成功
```

## 3. 当前问题和代码依据

### 3.1 课堂练习导入链路

当前后端流程如下：

```text
上传 PDF/DOCX
  → extract_document 提取题目候选
  → 遍历 extracted.fragments
  → 每道题调用 structure_candidate
  → 所有题目处理结束
  → ingest_structured_questions 入库
```

代码依据：

1. [document_import_tasks.py:149](../../apps/study/document_import_tasks.py#L149) 使用普通循环逐题处理。
2. [document_import_tasks.py:153](../../apps/study/document_import_tasks.py#L153) 对每道题调用一次 `structure_candidate`。
3. [document_structure_ai.py:172](../../apps/study/document_structure_ai.py#L172) 对每道题最多尝试两次。
4. [config/ai_config.cfg:295](../../config/ai_config.cfg#L295) 使用 `qwen3.7-plus`，单次请求超时为 300 秒，配置重试次数为 0。
5. [document_import_tasks.py:146](../../apps/study/document_import_tasks.py#L146) 成功结果暂存在当前进程的 `valid` 列表中。
6. [document_import_tasks.py:163](../../apps/study/document_import_tasks.py#L163) AI 逐题循环结束后才开始统一调用入库流程。

入库函数内部虽然按题目使用独立事务，但入库开始时间仍然被推迟到全部 AI 处理结束之后；因此单题成功结果不能及时落库，也不能在任务中断后直接恢复。

### 3.2 前端轮询不是根因

[course-practice.vue:1671](../../uniapp/src/pages/teacher/course-practice.vue#L1671) 的轮询只查询任务状态，间隔约 3 秒，不会重复触发导入或 AI 请求。前端看到大量 status 请求是长任务的表现，不是耗时来源。

### 3.3 错题练习题导入复用同一链路

错题练习题上传入口在 [classroom_wrong_drill_views.py:86](../../apps/missions/classroom_wrong_drill_views.py#L86) 调用 `create_course_document_import`，最终仍然执行 `process_document_import_task` 和 `structure_candidate`。

`import_purpose='wrongbook_drill'` 只影响 AI 结构化完成后的隔离入库和错题源绑定，见 [document_import_tasks.py:175](../../apps/study/document_import_tasks.py#L175)。因此错题练习题 DOCX 导入同样会受到逐题串行、单题长超时、失败重试和无题目级断点的影响。

### 3.4 错题精练生成是另一个问题

错题精练生成使用固定导入题和题号映射，不调用文档结构化 AI。当前按学生循环创建题目关系并生成 PDF，见 [classroom_wrong_drill_service.py:401](../../apps/missions/classroom_wrong_drill_service.py#L401)，应作为第二阶段单独优化，不能与文档 AI 导入慢混为一个问题。

### 3.5 队列配置存在生产核对项

当前代码将文档任务路由到 `document.import`，见 [settings.py:125](../../config/settings.py#L125)。但部署指南中的 worker 示例只监听 `celery,ai.batch`，见 [部署指南_v4.0.md:675](../260722_项目新部署指南/部署指南_v4.0.md#L675)。

生产截图已经证明示例任务进入过 `structuring` 阶段，但仍需确认实际生产 worker 是否监听 `document.import`，避免出现任务提交成功但长时间排队的第二类问题。

## 4. 修复目标和非目标

### 4.1 修复目标

- 题目级有限并发，缩短整体等待时间。
- 每道题单独持久化状态和结果，支持断点恢复。
- 单题失败不影响其他题，支持单题重试。
- 课堂练习和错题练习题共用优化后的基础能力，但保持业务数据隔离。
- 前端能看到已处理题数、当前阶段、失败题数和最终结果。
- 保留现有题目去重、图片资源处理、错题映射、权限和快照语义。

### 4.2 本方案不改变的内容

- 不允许 AI 凭空生成缺失答案。
- 不改变题目内容指纹和重复题处理规则。
- 不把错题练习题导入到课堂练习题或课程题目链接中。
- 不把错题练习题和课堂反馈报告合并成同一个任务。
- 不通过提高并发量绕过 AI 服务商限制。

## 5. 总体目标架构

### 5.1 推荐任务模型

建议保留现有 `QuestionDocumentImportTask` 作为文档导入父任务，并增加题目级处理记录。除非有明确的数据迁移理由，不要再创建名称相近的第二套父任务模型。题目任务业务名称可以按现有项目规范确定，至少应具备以下字段：

```text
QuestionDocumentImportTask（现有父任务，优先扩展而不是重复创建）
  id
  import_purpose              document_import / wrongbook_drill
  source_file
  document_fingerprint
  stage                       queued / extracting / structuring / importing / success / partial_success / failed
  total_questions
  success_count
  skipped_count
  failed_count
  progress
  error_summary

DocumentImportQuestionTask（新增题目级任务）
  id
  document_task_id
  source_position
  question_no
  source_fingerprint
  status                      pending / dispatched / running / success / failed / retrying
  ingest_status               pending / ingesting / ingested / failed
  retry_count
  structured_result_json
  ingest_error_code
  ingest_error_message_safe
  error_code
  error_message_safe
  started_at
  completed_at
  worker_heartbeat_at
  prompt_version
  model_name
```

题目级记录必须有唯一约束，例如：

```text
document_task_id + source_position
```

不能只用显示题号作为唯一键，因为同一文档不同章节可能重复使用题号。

### 5.2 目标处理流程

```text
上传与校验
  ↓
父任务记录 + 文档级候选题记录
  ↓
有限并发题目任务（建议初始 4～6）
  ├─ 成功：保存结构化结果，进入入库队列
  ├─ 可重试错误：退避后重试
  └─ 不可重试错误：保存失败原因，继续下一题
  ↓
分批入库（例如每 20～50 题一批）
  ↓
更新父任务统计和最终状态
```

父任务只负责编排和汇总，不能再次把所有题目结果放在进程内存中等待最后统一处理。

题目任务的 AI 状态和入库状态必须分开。`status=success` 只能表示题目结构化成功，不能表示题目已经完成数据库入库；只有 `ingest_status=ingested` 后，父任务才可以将该题计入最终完成数。这样可以覆盖“AI 结果已保存但入库 worker 在下一步宕机”的恢复场景。

### 5.3 跨进程数据和资源生命周期（实施前置条件）

题目级 Celery 子任务运行在不同进程，甚至可能运行在不同机器，不能直接接收父任务中的 `ExtractedQuestionFragment` 对象或依赖父任务的临时目录。父任务完成提取后必须持久化：

- 候选题文本、表格、题号、来源位置、页码范围和章节路径；
- 原始图片引用、页码、bbox 和资源清单；
- 文档内容指纹、候选题指纹、解析器版本；
- 子任务需要读取的临时资源路径或对象存储地址。

父任务的提取阶段也必须可恢复：提取完成后先保存文档级候选记录和候选总数，再进入题目任务投递。若提取或候选记录创建中途失败，恢复任务必须通过文档指纹和 `source_position` 幂等补齐记录，不能重复创建候选题或直接进入 AI 阶段。

临时资源的所有权必须归父任务或独立资源清理任务，只有在以下条件全部满足后才能删除：

1. 所有题目任务已进入最终状态；
2. 所有入库批次已完成；
3. 错题练习题源绑定和映射校验已完成；
4. 没有待重试题目或仍在运行的租约。

多 worker/多机器部署时，`source_file` 和资源目录必须位于所有 worker 可访问的共享存储；不能假设每个 worker 的本地磁盘内容相同。资源清理必须具备幂等性和保留期限，防止任务异常后永久泄漏或过早删除。

## 6. 具体修复方案

### 6.1 P0：先修正生产队列和监控

实施内容：

1. 确认生产 worker 是否监听 `document.import`。
2. 建议为文档导入部署独立 worker，例如只消费 `document.import`。
3. 文档导入 worker 使用适度并发；并发数不应简单等于 16，应以 AI 服务商限额、机器内存和请求 P95 为准。
4. 保留 `prefetch_multiplier=1`、late acknowledgement 等长任务保护配置。
5. 增加队列长度、任务排队时间和 worker 心跳监控。

建议的队列隔离：

```text
document.import  → 文档解析和题目结构化
ai.batch         → 其他题目 AI 批处理
ai.guidance      → 学生引导实时/异步任务
ai.feedback      → 课堂反馈任务
```

验收要求：任务提交后能够确认“已排队、已开始、当前题号”，不能只看到数据库状态长期停留在 `queued`。

### 6.2 P0：改为题目级持久化和有限并发

实施内容：

1. 父任务完成文档提取后，立即创建题目级记录。
2. 由 Celery group、任务调度器或等价机制投递题目级任务。
3. 并发初始值建议为 4～6，并使用现有 Qwen provider limiter 统一限流。
4. 每题任务必须幂等：如果状态已经是 `success`，重复投递时直接返回；如果是超时遗留的 `running`，只能在租约过期后回收。
5. 每题成功后立即写入 `structured_result_json`，并更新父任务计数。
6. 每题失败只记录该题失败，不得让整个文档任务回滚。

不要把 Celery group/chord 的回调作为唯一完成依据。父任务最终状态必须通过数据库中题目任务的最终状态汇总，且子任务投递要有可恢复机制。建议采用“数据库待调度记录 + 有限窗口 dispatcher”：只投递未完成且未被租约占用的题目，避免一次性把数百个任务全部推入队列。

理论耗时示例：318 道题平均每题 30 秒时，串行约 159 分钟；6 并发的纯计算等待约 27 分钟，实际还要叠加 AI 排队、入库、失败重试和资源处理时间。该数字是容量估算，不是生产 SLA 承诺。

### 6.3 P0：支持断点恢复和失败题重试

实施内容：

- worker 中断后，将超过租约时间的 `running` 题目恢复为 `pending`。
- 父任务恢复时只投递 `pending`、`retrying` 和租约失效的 `running` 题目。
- `success` 题目不重复调用 AI。
- 提供“重试失败题”能力，只重试失败题，不重新处理整份文档。
- 保存失败题号、错误类型、重试次数和最后失败时间。
- 达到最大重试次数后进入 `failed`，不再自动循环重试。

现有 `process_document_import_task` 声明 `max_retries=0`，整任务异常后不能依靠 Celery 自动恢复；因此题目级记录和任务租约是必须项，不是可选的体验优化。

题目任务必须明确唯一的重试责任。建议由题目级任务统一负责业务重试，AIClient 不再对同一类错误重复重试；或者明确采用相反的责任划分，但不能同时让 Celery、业务函数和 AIClient 各自重试。数据库写入、计数更新和状态转换也必须幂等，防止 late acknowledgement 或网络重投递造成重复入库。

还需要增加一个调度恢复任务，定期扫描以下记录并重新投递：

- `pending` 且长时间未投递的题目；
- `dispatched` 但没有开始时间的题目；
- 租约已过期的 `running` 题目。

这样可以覆盖“数据库事务已提交但消息投递失败”以及 worker 在投递后立即宕机的情况。

### 6.4 P1：缩短并细化 AI 请求预算

当前文档结构化请求的单次超时为 300 秒，且 `structure_candidate` 对响应错误和请求错误统一进行第二次尝试。

建议：

1. 文档结构化使用独立的超时配置，不要被所有 AI 任务强制共用 300 秒。
2. 先根据生产 P95 设置 60～120 秒的起始值，再通过日志调整。
3. 仅对超时、429、502/503、网络暂时不可用等临时错误重试。
4. JSON 格式错误优先使用一次低成本修复请求，或直接将题目标记为失败；不要无条件重复完整请求。
5. 设置单题总耗时上限，例如请求、重试、退避和排队时间合计不得无限增长。
6. `max_tokens=8192` 应根据实际结构化结果长度重新评估；若输出通常较短，可降到 2048～4096。
7. 保留严格 JSON/schema 校验，不能为了速度放弃结构化结果校验。

注意：缩短超时必须先通过生产数据确认，不能直接改成过小值导致正常长题大量失败。

当前 [apps/common/ai/config.py](../../apps/common/ai/config.py#L469) 对非引导类任务要求 `timeout_seconds` 必须为 300。因此文档结构化使用 60～120 秒前，必须同步增加文档任务的独立配置类型，并更新配置校验、配置测试和部署配置；只修改 `config/ai_config.cfg` 不足以生效。

建议最终明确以下错误归属：

| 错误类型 | 建议处理 |
|---|---|
| 超时、429、502/503、暂时性网络错误 | 题目任务退避重试 |
| JSON 解析失败 | 一次轻量修复请求或直接失败，不重复完整请求 |
| schema 校验失败 | 记录结构化失败，必要时进入人工复核 |
| 参数、凭据、代码配置错误 | 不重试，立即告警 |

修复请求要有独立 prompt/schema、最大次数和成本上限，不能将其隐藏在原有的第二次完整调用中。

### 6.5 P1：增加 AI 前缓存和跳过重复处理

当前题目内容指纹主要在 AI 结构化完成后用于去重，重复上传同一文档仍可能先重复调用 AI。建议增加 AI 前缓存：

```text
文档指纹
+ 题目来源位置
+ 候选题文本指纹
+ prompt 版本
+ 模型版本
→ 已有成功结构化结果时直接复用
```

缓存命中时必须复用已验证的结构化结果，并重新建立本次导入的来源引用；不能只复用题库关联而丢失本次文档位置。

缓存失效条件至少包括：

- 候选题文本发生变化；
- prompt 版本发生变化；
- 结构化 schema 发生变化；
- 模型版本发生变化；
- 历史结果被标记为需要人工复核。

缓存不能直接使用只包含题干和选项的文档来源指纹。当前 [document_import_service.py:496](../../apps/study/document_import_service.py#L496) 的来源指纹不包含图片内容；带图题缓存键还必须包含图片资源清单或资源哈希。缓存结果必须同时校验 schema、解析器版本、prompt 版本、模型版本和资源版本，避免复用错误的图形或过期结果。

### 6.6 P1：减少图片资源处理的重复开销

当前每道候选题处理图片时可能重复打开同一个 PDF/DOCX，并按题目提取内部资源。建议：

- 文档级打开句柄或建立资源索引；
- 同一 `pdf:xref` 或 DOCX media 引用只提取一次；
- 题目任务只读取已落盘的临时资源；
- 导入完成或失败后统一清理临时目录；
- 记录资源提取耗时，避免把图片问题误判为 AI 慢。

这项优化不是小时级耗时的第一根因，但并发处理后可以减少磁盘和 CPU 争用。

### 6.7 P1：分批入库和结果汇总

建议每道题成功后先落题目级结果，再由独立入库步骤按小批次处理。不能直接无参数重复调用现有 `ingest_structured_questions`，因为该函数会在自己的调用范围内创建 paper、完成批次统计并结束 ingestion batch。

必须增加“文档级入库上下文”，由父任务在开始入库阶段创建一次 paper，并将 paper ID、batch ID、导入目的和资源根目录传给所有入库批次。批次入库只负责创建/去重题目、导入资源和建立关联，不得提前完成父批次。

要求：

1. 入库过程保持现有指纹去重和图片导入规则。
2. 每批入库必须幂等，重复执行不会重复创建题目。
3. 课堂练习继续建立课程/目录关联。
4. 错题练习题继续使用 `import_purpose='wrongbook_drill'`，不建立普通课程题目链接。
5. 错题源在题目级结果完成后建立 `ClassroomWrongDrillSourceQuestion`，不要等待所有题目都成功才保存第一条结果。
6. 父任务最终状态根据成功、跳过和失败数量确定：
   - 全部成功或跳过：`success`；
   - 有成功且有失败：`partial_success`；
   - 全部失败：`failed`。

最终 `finish_ingestion_batch` 只能由父任务在所有题目任务、所有入库批次和业务绑定完成后调用一次。父任务需要累计各批次的 `created_count`、`skipped_existing_count`、`skipped_in_package_count` 和 `failed_count`，不能使用最后一个批次的局部计数覆盖全量结果。整份文档只能创建一个对应 paper，除非业务明确要求按章节创建多个 paper。

现有指纹去重在串行流程中使用内存集合识别同批次重复题。并发后必须增加数据库级协调：

- 父任务先按文档来源位置建立稳定候选记录；
- 同一批次的相同候选指纹只允许一个代表任务执行 AI，其他记录作为 alias/source reference；
- 内容指纹发生 `reserving` 冲突时要等待或重新读取最终结果，不能因为短暂未激活就直接记为失败；
- 题库唯一约束和来源引用写入必须具备幂等更新。

这项处理必须覆盖“同题号不同内容”和“同内容不同来源位置”两种情况。

### 6.8 P0：错题练习题源绑定的并发安全

当前 [classroom_wrong_drill_service.py:126](../../apps/missions/classroom_wrong_drill_service.py#L126) 的 `finalize_source_import` 会删除现有源题目后按 `valid_questions` 全量重建。因此错题题目子任务不能直接逐题调用当前 finalizer。

推荐流程：

```text
题目子任务完成
  → 保存题目级结构化结果
  → 父任务确认所有题目进入最终状态
  → 一次性执行 source_set 绑定/映射
  → 映射完成后才允许 source_set=ready
```

如果必须增量展示源题目，则需要将 finalizer 改为按 `source_position` 幂等 upsert，并增加版本号、锁和最终一致性检查。无论采用哪种方式，都不能让后完成的子任务删除先完成的结果。

错题练习题导入和映射校验必须有独立状态：AI 解析未完成、映射表未校验、存在必需字段缺失时，均不得进入 `ready`，也不得触发错题精练生成。

### 6.9 P0：provider 配额和业务公平性

当前 Qwen provider 是全局并发限制，默认上限为 6，见 [provider_limiter.py:24](../../apps/common/ai/provider_limiter.py#L24)。文档导入使用 4～6 并发时，可能占满其他 AI 业务的容量。

需要在 dispatcher 层设置文档导入专用配额和最低保障，例如限制文档导入最多使用总容量的一部分；同时记录 provider lease 等待时间。不能只提高 worker concurrency，因为 provider limiter 仍会排队，甚至让大量 worker 长时间占用进程等待。

Redis 限流不可用时，当前代码会退回进程内 semaphore，跨多个 worker 时不能完全保证全局上限。因此 Redis 异常时应告警并降低文档调度量，不能把进程内 fallback 当成全局限流。

## 7. 课堂练习和错题练习题的业务适配

### 7.1 课堂练习导入

课堂练习保持当前业务结果：

```text
题目结构化
→ 题库去重
→ 课程题目/目录关联
→ 来源文档引用
```

优化只改变处理时机和任务组织方式，不改变题目字段、题目去重和课程关联语义。

### 7.2 错题练习题导入

错题练习题保持隔离：

```text
题目结构化
→ 题库去重或创建规范题目
→ 绑定 ClassroomWrongDrillSourceSet
→ 等待映射表校验
→ 建立错题练习题号到课堂原题号的映射
```

建议同时优化以下体验：

1. 映射表在上传时立即校验，不必等待全部 AI 题目完成。
2. DOCX 导入和映射表校验使用同一个 `source_set`，但状态分开保存。
3. 前端轮询并展示错题练习题导入的题目级进度，目前上传后主要是刷新源列表，无法完整展示长任务进度。
4. 未完成 AI 解析或映射校验时，源状态不能标记为 `ready`。
5. 缺少答案、题号重复、题号无法映射的题目单独记录，不得静默加入精练作业。

错题源的最终绑定必须以父任务汇总结果为准。当前 `finalize_source_import` 会全量删除并重建源题目，因此在没有改造 finalizer 前，不能按题目子任务逐条调用它；必须等待所有题目任务结束后统一绑定。映射表可以提前校验，但只能在 AI 解析、题目绑定和映射校验均完成后将源标记为 `ready`。

当前前端选择文件时允许 PDF，但后端错题源接口只接受 DOCX。实施时必须统一产品口径：如果错题练习题只支持 DOCX，前端应去掉 PDF 选项；如果要支持 PDF，则必须同时补充 PDF 的题号/资源/映射验收，不能仅依赖前端放开后缀。

### 7.3 错题精练生成单独处理

文档导入优化完成后，错题精练生成仍建议进行以下独立优化：

- 按学生拆成可恢复的子任务；
- 批量预取学生错题、映射和题目快照；
- 每个学生完成后立即更新 package 状态；
- PDF 生成与数据库事务解耦；
- 避免整个班级所有学生共用一个长事务；
- 生成失败时只重试失败学生。

这些措施解决的是班级人数较多时的 PDF/数据库耗时，不是本文档所述的 AI 结构化慢问题。

## 8. 前端状态和接口调整

状态接口建议至少返回：

```json
{
  "stage": "structuring",
  "progress": 46,
  "total_questions": 318,
  "success_count": 140,
  "skipped_count": 20,
  "failed_count": 2,
  "running_count": 6,
  "running_question_nos": ["156", "157", "160"],
  "last_heartbeat_at": "2026-09-16T12:00:00Z",
  "retryable_failed_count": 1

```

前端要求：

- 继续轮询，但展示“已完成/总数”，不能只展示百分比；
- 长时间无心跳时提示“任务可能需要恢复”，不能直接提示失败；
- 成功、部分成功、失败后停止轮询；
- 支持查看失败题和单独重试失败题；
- 课堂练习和错题练习题使用相同状态协议，按 `import_purpose` 展示不同业务文字。

并发处理时不存在唯一可靠的“当前题号”，因此接口应返回 `running_question_nos` 或最近开始/完成的题目列表，不能只保留一个 `current_question_no`。错题练习题上传接口还需要明确通过 `task_id` 或 `source_set_id` 获取同一套状态数据，避免只刷新源列表而无法判断 AI 是否仍在运行。

## 11. 验收标准

### 11.1 功能正确性

- 课堂练习导入成功后，题目内容、题型、答案、解析、图片、课程关联和去重结果与现有规则一致。
- 错题练习题导入成功后，题目只绑定到对应 `wrongbook_drill` 源，不进入普通课堂练习关联。
- 错题练习题映射方向正确：例如精练题 5、6、7 指向课堂原题 4 时，学生错题 4 生成精练题 5、6、7。
- 重复上传不会重复创建题目或重复建立来源引用。
- AI 失败题不会阻塞其他题，最终状态正确显示为部分成功。

### 11.2 恢复能力

- 在处理过程中停止 worker，重新启动后能继续未完成题目。
- 已成功题目不会再次调用 AI。
- 单题重试只影响该题。
- 任务重复投递不会重复入库。
- 临时图片资源不会长期泄漏。
- 父任务已提交但子任务消息投递失败时，dispatcher 能重新投递，不会长期停留在 `pending`。
- 父任务只创建一个 paper，批次总数不会被某个入库子批次覆盖。
- AI 结构化成功但入库中断时，恢复任务只重放入库，不重复调用 AI。
- 错题源全量绑定不会因子任务完成顺序不同而丢题或重复建题。

### 11.3 性能目标

以 300～350 道题文档为验收样本，至少确认：

- 不再以单个长任务串行等待全部 AI 请求；
- 题目级并发受控且不超过 provider 限额；
- 正常请求下整体耗时相较原串行模型显著下降；
- 队列等待、AI 请求、重试、入库耗时均可单独统计；
- 单个异常题不会把整份文档拖到数小时；
- 生产环境不出现任务长期停留在 `queued` 或无心跳状态。

性能验收不应只看平均耗时，还要检查 P95、失败重试耗时和 worker 重启后的恢复耗时。

### 11.4 并发一致性验收

必须额外验证：

- 同一批次存在相同内容的重复候选题；
- 同一题号在不同章节出现但内容不同；
- 多个题目任务同时争抢相同内容指纹；
- 子任务完成顺序与文档顺序不同；
- 入库子批次重复执行；
- worker 在图片已提取但 AI 尚未完成时重启；
- 错题源部分题目失败、部分题目成功且存在映射表；
- Redis provider 限流暂时不可用。

## 12. 修复有效性确认

根据当前代码链路和补充后的目标架构，可以确认：

1. 逐题串行是当前小时级耗时的主要原因；改为有限并发后，整体等待时间将从“所有题目耗时相加”变为“分批并行耗时”。
2. 题目级持久化会消除“成功结果只在内存中，任务中断后全部丢失”的问题。
3. 单独的超时、重试和缓存策略会减少异常题对整体任务的拖累。
4. 队列核对会排除生产配置导致的额外排队。
5. 课堂练习和错题练习题共用同一导入优化框架，因此两种文档导入的慢问题都能覆盖解决。
6. 错题精练生成不依赖文档结构化 AI，需要按学生/PDF 任务另行优化，但不会再继承本文档所述的逐题 AI 串行瓶颈。

因此，补齐“跨进程候选题和资源持久化 → 文档级入库上下文 → 并发去重 → 错题源 finalizer 一致性 → 调度投递恢复 → provider 配额隔离”后，再按“队列核对 → 题目级任务 → 有限并发 → 持久化断点 → 精细重试 → 分批入库 → 性能验收”的顺序实施，方案能够针对性解决课堂练习和错题练习题导入慢的问题。

如果只实施增加并发而不实施上述一致性约束，不能确认稳定解决，且可能引入重复题、重复 paper、错题源丢题或批次统计错误。最终上线前仍必须使用生产规模文档和真实 AI 服务完成压力、失败恢复、队列投递和数据一致性验收。
