# 登录端角色自动开通优化实施方案

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 文档日期 | 2026-08-20 |
| 适用范围 | 短信验证码登录、微信一键登录、微信手机号绑定、账号多角色授权 |
| 需求类型 | 家长角色首次登录自动开通；保持教师/管理员授权边界 |
| 实施策略 | 先完成短信登录链路，再同步微信登录和微信绑定 |
| 预期改动级别 | 中小规模，原则上无需数据库表结构迁移 |
| 当前状态 | 已按本方案完成代码实现，待具备数据库环境后执行完整回归 |

## 2. 需求概述

当前登录页允许用户选择“家长”角色，但已有账号在没有 `UserRole(parent)` 时，登录接口会直接返回 `ROLE_NOT_GRANTED`，不会自动创建家长角色。

本次需求调整为：

> 用户完成短信验证码验证，并主动选择 `parent` 角色登录时，如果该账号此前没有家长角色，则自动创建并开通该账号的家长角色。

自动开通只代表获得进入家长端和提交绑定申请的资格，不代表自动拥有任何学生数据访问权限。家长仍需通过学生确认后形成有效的 `StudentParentBind` 关系，才能查看学生数据。

## 3. 当前代码逻辑与问题定位

### 3.1 短信登录链路

前端登录页在选择角色后，将手机号、验证码和 `role_type` 提交到 `/auth/login`：

- `uniapp/src/pages/login/index.vue`
- `uniapp/src/api/index.ts`

后端登录逻辑位于 `apps/accounts/views.py`：

1. 校验手机号和验证码。
2. 读取请求中的 `role_type`，默认值为 `student`。
3. 新账号仅允许自助创建 `student` 或 `parent` 角色。
4. 已有账号请求 `parent` 时，先执行家长角色幂等开通策略；请求其他角色时，必须通过 `has_user_role(user, active_role)` 校验。
5. 校验通过后生成绑定 `active_role` 的 JWT。

问题发生在已有账号分支：

```text
已有账号
  -> has_user_role(user, parent)
  -> 没有 parent 授权
  -> 直接返回 ROLE_NOT_GRANTED
```

后续的 `get_or_create_user()` 对已有账号只更新登录时间，不会增加角色。因此当前实现无法满足“已有账号首次选择家长登录时自动开通 parent”的要求。

本次实现已将该分支调整为：仅在身份验证成功且主动选择 `parent` 时调用登录场景专用的幂等开通服务；`teacher`、`admin` 仍沿用原有授权校验。

### 3.2 角色模型

系统同时存在两类角色信息：

- `UserAccount.role_type`：历史默认角色和兼容字段。
- `UserRole`：当前多角色授权表，使用 `(user, role)` 唯一约束。

`active_role` 是当前 JWT 会话角色。多角色账号登录或切换时，应只改变当前会话的 `active_role`，不能覆盖数据库中的原始 `role_type`。

### 3.3 家长绑定链路

当前绑定流程为：

```text
学生生成绑定码
  -> 家长提交绑定申请
  -> 学生确认
  -> StudentParentBind.bind_status = active
  -> 信号授予 parent/student 角色
```

但是家长提交绑定申请本身要求当前会话已经拥有 `parent` 角色。因此首次家长登录必须先完成角色开通，否则首次绑定流程无法开始。

## 4. 目标与非目标

### 4.1 本次目标

1. 短信验证码验证成功后，主动选择 `parent` 的已有账号可自动开通家长角色。
2. 新账号首次选择 `parent` 的行为保持不变。
3. 自动开通不覆盖账号已有的学生、教师或管理员角色。
4. 自动开通后可以进入家长端，并看到无孩子时的绑定引导。
5. 微信登录和微信绑定复用相同的家长角色开通规则。
6. 保持教师、管理员角色不能通过普通登录自助获得的安全边界。
7. 角色创建具备幂等性和并发安全性。

### 4.2 非目标

1. 不修改 `UserAccount.role_type` 的历史语义。
2. 不自动创建或激活学生-家长绑定关系。
3. 不改变学生确认绑定的业务流程。
4. 不允许通过选择 `parent` 自动获得 `teacher` 或 `admin`。
5. 不在本次需求中重构全部权限系统。

## 5. 目标业务规则

| 账号情况 | 请求角色 | 处理结果 |
|---|---|---|
| 不存在 | student | 创建账号并授予 student |
| 不存在 | parent | 创建账号并授予 parent |
| 不存在 | teacher/admin | 拒绝，返回 `ROLE_NOT_GRANTED` |
| 已存在且已有 active parent | parent | 正常登录 |
| 已存在且没有任何 parent 记录 | parent | 创建 active parent 后登录 |
| 已存在且 parent 记录为 inactive | parent | 拒绝，不自动恢复已撤销角色 |
| 已存在但没有 active student | student | 按现有规则拒绝 |
| 已存在但没有 active teacher/admin | teacher/admin | 按现有规则拒绝 |
| 已存在拥有多个角色 | 任一已授权角色 | 登录当前请求角色，不修改其他角色 |

“没有任何 parent 记录”指 `UserRole` 中没有该账号的 parent 行。对于历史数据中 `role_type=parent` 但缺失 `UserRole` 的兼容账号，可以在首次登录时补齐 active parent 记录。

如果产品明确要求“被撤销的家长角色也可以通过短信重新开通”，需要单独调整规则；本方案默认保留撤销的约束，避免登录流程绕过管理员或业务侧的角色撤销操作。

## 6. 总体设计

### 6.1 角色开通原则

新增一个面向登录场景的角色解析/开通服务，例如：

```text
resolve_login_user_and_role(mobile, requested_role, auth_context)
```

该服务负责：

1. 查找或创建账号。
2. 判断账号状态是否为 active。
3. 根据请求角色执行授权策略。
4. 对首次 parent 登录执行幂等授权。
5. 返回可用于生成 JWT 的用户和会话角色。

不要把 `get_or_create_user()` 改成“已有账号总是自动增加传入角色”。该函数还被微信绑定等流程复用，扩大其语义可能导致教师或管理员角色被错误自助开通。

### 6.2 推荐处理流程

```text
POST /auth/login
  -> 校验手机号和短信验证码
  -> 校验 requested_role 是否为合法角色
  -> 在事务中查找/创建用户
  -> 校验用户状态为 active
  -> requested_role == parent ?
       无 UserRole(parent) 记录 -> 创建 active parent
       有 active 记录 -> 继续
       有 inactive 记录 -> ROLE_NOT_GRANTED
     其他角色 -> 必须已有 active 授权
  -> 生成 active_role 对应 JWT
  -> 返回 user.roles 和 active_role
```

### 6.3 事务与并发

角色开通必须放在事务中，并依赖数据库唯一约束保证幂等：

- `UserAccount.mobile` 保证账号唯一。
- `UserRole(user, role)` 唯一约束保证角色唯一。
- 已有账号角色开通时，优先锁定用户记录或使用可靠的并发重试策略。
- 重复点击登录、双端同时登录、并发请求都不能产生重复 `UserRole`。

### 6.4 授权来源

建议将通过登录自助创建的角色记录标记为 `self_login`，不要继续全部记录为 `business`。如果需要区分来源，可以让 `grant_user_role()` 支持传入 `grant_source`，默认仍保持 `business`，登录场景显式传入 `self_login`。

## 7. 分阶段实施计划

### 阶段一：短信登录链路

#### 后端

修改范围：

- `apps/accounts/views.py`
- `apps/accounts/services.py`
- `apps/accounts/roles.py`（如需增加角色状态查询辅助方法）

实施要点：

1. 保留验证码校验和合法角色校验。
2. 将已有账号的 parent 处理从“无授权即拒绝”调整为“无记录则幂等创建”。
3. parent 角色已有 inactive 记录时继续拒绝。
4. 不修改数据库中的 `UserAccount.role_type`。
5. 返回的 `user.roles` 应包含新创建的 `parent`。
6. 生成的 JWT 中 `active_role` 必须为 `parent`。
7. 其他角色沿用原有授权策略。
8. 登录时应确认账号 `status=active`，停用账号不能通过自动开通绕过状态限制。

#### 前端

短信登录前端已有以下行为，原则上无需改动：

- 家长 Tab 设置 `activeTab=parent`。
- 调用登录接口时传递 `role_type=parent`。
- 登录成功后保存 token 和用户信息。
- 按 `active_role=parent` 跳转到家长端。

建议只补充错误提示和回归验证，确保不再把正常的首次家长登录显示为“账号未开通此角色”。

### 阶段二：短信登录测试

建议在 `apps/accounts/tests/test_role_auth.py` 增加或调整以下测试：

1. 已有 student 账号首次以 parent 登录成功。
2. 登录后存在一条 active `UserRole(parent)`。
3. 数据库中的原始 `role_type` 仍为 student。
4. 返回的 `active_role` 为 parent，返回的 `roles` 包含 parent 和 student。
5. 同一账号重复 parent 登录不会创建重复角色。
6. 已有 active parent 账号可以正常登录。
7. inactive parent 角色不能通过登录自动恢复。
8. 新账号 parent 登录继续成功。
9. 新账号 teacher/admin 登录继续被拒绝。
10. 已有 student 账号 admin 登录继续被拒绝。
11. parent 登录后无绑定关系时，家长端接口返回空孩子列表或绑定引导状态。
12. parent 会话不能执行学生答题、提交等写操作。
13. 并发首次 parent 登录不会出现重复角色或未授权异常。

### 阶段三：微信一键登录

当前微信登录接口没有携带登录页选择的角色。为了使短信和微信行为一致，需要同步传递角色。

#### 前端改动

修改范围：

- `uniapp/src/api/wechat.ts`
- `uniapp/src/utils/wechat-auth.ts`
- `uniapp/src/pages/login/index.vue`

建议接口形式：

```text
wechatApi.login(code, roleType)
  -> POST /auth/wechat-login
     { code, role_type: roleType }
```

登录页调用微信登录时传入当前 `activeTab`。非微信环境的兼容逻辑保持不变。

#### 后端改动

修改范围：

- `apps/qrcode/views.py`
- 必要时抽取公共登录角色服务到 `apps/accounts/services.py`

已有 `WechatIdentity` 时：

1. 校验 `role_type`。
2. 如果选择 parent，复用短信登录的 parent 自动开通策略。
3. 如果选择 teacher/admin，仍要求已有对应授权。
4. 生成带正确 `active_role` 的 JWT。

没有绑定手机号时，继续返回 `bind_token`，不直接创建账号。

### 阶段四：微信绑定

当前微信绑定页已经允许用户选择学生或家长角色，但已有账号选择 parent 时仍要求先存在 parent 授权。

修改范围：

- `apps/qrcode/views.py` 中的 `wechat_bind`
- `apps/accounts/services.py` 中的公共角色解析服务
- `apps/accounts/tests/test_role_auth.py`

处理规则：

```text
微信身份 + 手机号验证码验证成功
  -> 新账号选择 student/parent：按原规则创建
  -> 已有账号选择 parent 且无 parent 记录：创建 parent
  -> 已有账号选择 parent 且为 inactive：拒绝
  -> 已有账号选择 teacher/admin 且无授权：拒绝
```

微信绑定必须与短信登录使用同一套 parent 开通策略，避免出现短信登录成功、微信绑定失败的渠道差异。

### 阶段五：文档、测试和发布验证

需要同步更新：

- 家长端功能实施文档中“已有学生账号不能自动获得 parent”的旧规则。
- 现有期望 `ROLE_NOT_GRANTED` 的测试。
- 登录、角色切换、微信登录的验收清单。
- 发布说明和回滚说明。

## 8. 接口契约

### 8.1 短信登录成功响应

接口仍为：

```text
POST /api/v1/auth/login
```

请求示例：

```json
{
  "mobile": "13800000000",
  "verify_code": "123456",
  "role_type": "parent"
}
```

响应中应满足：

```json
{
  "code": 0,
  "data": {
    "active_role": "parent",
    "user": {
      "active_role": "parent",
      "role_type": "parent",
      "roles": ["parent", "student"]
    }
  }
}
```

其中响应中的 `user.role_type` 是会话兼容字段，不代表数据库中的 `UserAccount.role_type` 被修改。

### 8.2 失败响应

以下情况继续返回 `ROLE_NOT_GRANTED`：

- 请求 teacher/admin 但账号没有对应授权。
- 请求 parent，但 parent 角色已被标记为 inactive。
- 账号已停用。

## 9. 权限和数据安全影响

### 9.1 权限影响

新增的 parent 角色只能访问已有家长端能力。家长查看学生数据仍需满足：

```text
active_role == parent
  -> 存在 active StudentParentBind
  -> 已选择有效孩子上下文
  -> 只读访问学生数据
```

自动开通不会：

- 自动绑定学生。
- 自动批准绑定申请。
- 允许家长代替学生答题或提交学习数据。
- 授予教师或管理员权限。

### 9.2 角色切换影响

已有学生账号首次家长登录后，返回角色列表会新增 parent。角色切换组件会显示家长选项，这是预期行为。

切换角色仍通过 `/auth/switch-role`，该接口只允许切换到已经 active 的角色。

### 9.3 数据库影响

本方案使用已有 `UserRole` 表和唯一约束，原则上不需要新增表或字段。

上线前建议检查：

1. 是否存在 `UserAccount.role_type` 为合法角色但缺少对应 `UserRole` 的历史账号。
2. 是否存在重复或异常的 `UserRole` 数据。
3. 是否存在状态为 inactive 的 parent 角色。
4. 生产数据库是否已经执行 `UserRole` 相关迁移。

历史兼容数据可以通过迁移脚本或首次登录时的规范化逻辑补齐，但不能把 inactive 角色无条件恢复为 active。

## 11. 验收标准

### 后端验收

- 已有 student 账号输入正确短信验证码并选择家长，可以返回 HTTP 200。
- `UserRole` 中存在一条 active parent 记录。
- 原账号已有角色仍然存在，`UserAccount.role_type` 未被改写。
- JWT 的 `active_role` 为 parent。
- 返回的角色列表包含 parent。
- parent 无绑定孩子时不能查看任何学生数据。
- teacher/admin 未授权时仍然无法通过登录自动开通。
- parent 角色撤销后不会被普通登录自动恢复。
- 重复或并发请求不会产生重复授权记录。

### 前端验收

- 登录页选择家长后，短信登录成功进入家长端。
- 家长端无绑定孩子时展示“添加孩子/绑定学生”引导。
- 角色切换能够在 student 和 parent 之间正常切换。
- 微信登录选择家长时行为与短信登录一致。
- 登录失败时能正确展示 `ROLE_NOT_GRANTED` 等业务错误。

## 12. 发布顺序与回滚方案

### 推荐发布顺序

1. 先发布后端公共角色开通服务和短信登录逻辑。
2. 执行后端单元测试、接口测试和并发测试。
3. 发布前端微信角色参数传递。
4. 发布微信登录和微信绑定后端逻辑。
5. 执行线上灰度账号验证。
6. 最后更新业务文档和验收记录。

### 回滚策略

如发现问题，可按以下顺序回滚：

1. 前端回滚微信角色参数传递，短信登录仍保持可用。
2. 后端关闭 parent 首次自动开通分支，恢复 `ROLE_NOT_GRANTED` 校验。
3. 已经创建的 parent 角色不建议直接删除，应根据业务决定保留、标记 inactive 或人工处理。
4. 不回滚 `UserRole` 表结构和已有角色数据，避免影响其他多角色功能。

## 13. 实施注意事项

1. 不要直接修改 `get_or_create_user()` 的已有账号行为，否则可能误放开教师或管理员角色。
2. 不要通过修改 `UserAccount.role_type='parent'` 实现多角色登录。
3. 不要因为自动创建 parent 就自动创建 `StudentParentBind`。
4. 短信登录、微信登录、微信绑定必须复用同一套角色策略。
5. 测试中要区分“没有角色记录”和“角色已被撤销”。
6. 角色开通成功后必须重新序列化用户角色列表，避免前端拿到旧的 `roles`。
7. 发布前检查现有测试中关于“已有学生账号选择 parent 必须拒绝”的断言，并按新需求调整。

## 14. 结论

本方案以登录时的显式角色选择作为家长角色开通条件，以手机号验证码或微信身份验证作为身份依据；只新增 parent 授权，不覆盖原有角色；以有效绑定关系作为学生数据访问的最终控制条件。

该方案改动范围可控，能够解决已有账号首次家长登录失败的问题，同时保持教师、管理员权限边界和家长只读数据隔离。

## 15. 复核补充：三角色切换与多端支持

### 15.1 多角色切换的业务定义

本系统支持的是“一账号多角色、一次激活一个角色、无需退出即可切换”，而不是同一前端页面同时保持三套前台会话。

例如账号同时拥有：

```text
UserRole(student)
UserRole(parent)
UserRole(teacher)
```

用户可以：

```text
登录学生端
  -> 用户信息中显示 student、parent、teacher
  -> 切换到家长端
  -> 切换到教师端
  -> 再切换回学生端
```

每次切换都会由 `/auth/switch-role` 签发一组绑定新 `active_role` 的 JWT，并更新前端保存的当前会话。前端不会要求用户重新输入短信验证码，也不会执行退出登录流程。

当前前端只保存一组 access token、refresh token 和 userInfo，因此不承诺三个角色在三个浏览器窗口中同时保持独立前台会话；如果未来需要多窗口独立会话，需要单独设计多会话 Token 存储。

### 15.2 多端角色切换入口

角色切换必须在以下平台全部可见：

| 平台 | 学生端入口 | 家长端入口 | 教师端入口 | 管理员端入口 |
|---|---|---|---|---|
| H5 | StudentSidebar | ParentSidebar | TeacherSidebar | Admin Home |
| APP-PLUS | StudentSidebar | ParentSidebar | TeacherSidebar | Admin Home |
| 微信小程序 | MpDrawer | MpDrawer | 按教师端实际布局提供 | Admin Home |

学生端不能再使用“仅 H5 显示角色切换”的条件。APP-PLUS 应与 H5 共用学生侧栏中的 `RoleSwitcher`；微信小程序继续通过 `MpDrawer` 提供入口，避免重复渲染。

### 15.3 三角色切换实现要求

后端：

1. `UserRole` 中存在 active 的 student、parent、teacher 时，`serialize_user_session()` 必须返回三个角色。
2. `/auth/switch-role` 必须允许在任意两个已授权角色之间切换。
3. 切换后的 JWT `active_role` 必须与请求角色一致。
4. 切换不能修改 `UserAccount.role_type`，不能撤销或覆盖其他角色。
5. 账号停用后，角色切换、Token 刷新和 JWT 鉴权都必须失败。

前端：

1. `RoleSwitcher` 根据 `userInfo.roles` 展示全部 active 角色，而不是写死两个角色。
2. 切换成功后保存新的 Token 和 userInfo。
3. 根据服务端返回的 `active_role` 使用统一的 `routeForRole()` 跳转。
4. 学生、家长、教师、管理员页面均应能打开角色切换入口。
5. 微信绑定成功后也必须根据返回的 `active_role` 跳转，不能固定跳转学生首页。

### 15.4 微信登录和绑定补充要求

微信一键登录必须将登录页当前选择的角色传给后端：

```json
{
  "code": "微信临时登录凭证",
  "role_type": "parent"
}
```

已有微信身份登录时：

- 选择 parent 且不存在 parent 记录：自动创建 parent。
- 选择 parent 且 parent 已 inactive：拒绝登录。
- 选择 teacher/admin：仍然要求已有对应授权。

微信手机号绑定成功后：

- 返回 `active_role=parent` 时进入家长端。
- 返回 `active_role=student` 时进入学生端。
- 不允许固定跳转 `/pages/student/mp-home`。

### 15.5 三角色和多端测试要求

新增或调整以下测试：

1. 一个账号拥有 student、parent、teacher 三个角色时，可以连续切换三种角色。
2. 每次切换返回的 `active_role` 正确。
3. 三角色列表顺序和内容正确，且不重复。
4. H5 学生端显示角色切换。
5. APP-PLUS 学生端显示角色切换。
6. 微信小程序学生端通过 `MpDrawer` 显示角色切换。
7. 家长、教师、管理员端均能显示角色切换。
8. 微信绑定选择 parent 后进入家长端。
9. 微信绑定选择 student 后进入学生端。
10. 切换角色不要求重新输入验证码。
11. 切换角色不会删除或覆盖其他角色授权。
12. 停用账号已有 Token 后，切换、刷新和接口访问均失败。

### 15.6 本次复核后的验收结论

只有同时满足以下条件，才认为三角色多端需求完成：

```text
账号拥有 student + parent + teacher
  -> H5、APP-PLUS、微信小程序均有可见切换入口
  -> 任意角色登录后可以切换到另外两个角色
  -> 页面按 active_role 正确跳转
  -> 不重新输入验证码、不执行退出登录
  -> 学生、家长、教师权限仍按各自角色隔离
```

## 17. 五类角色转换操作方案

### 17.1 角色体系说明

本系统需要区分“账号全局角色”和“机构内成员角色”：

| 类型 | 数据位置 | 可选角色 | 作用 |
|---|---|---|---|
| 账号全局角色 | `UserRole` | `admin`、`teacher`、`parent`、`student` | 决定登录端、权限范围和角色切换 |
| 机构成员角色 | `InstitutionMember` | 机构管理员、教师 | 决定账号在某个机构中的管理或教学权限 |
| 班级学生关系 | `ClassStudent` | 学生关系 | 决定账号是否属于某个班级，并触发学生角色 |
| 家长绑定关系 | `StudentParentBind` | 家长-学生关系 | 决定家长能否查看具体学生数据 |

机构详情页面中的“机构管理员、教师”不是账号全部角色。家长和学生不属于机构成员角色，应通过家长绑定、班级关系或全局角色授权产生。

### 17.2 转换一：学生账号转为教师账号

#### 当前支持情况

当前支持，但必须由机构管理员操作，不能仅在登录页选择“教师”自动获得。

#### 操作步骤

1. 使用机构管理员进入“机构详情”。
2. 在“成员管理”中输入该学生账号的原手机号和姓名。
3. 角色选择“教师”。
4. 填写科目和学段。
5. 点击“添加成员”。
6. 学生账号退出当前会话后，重新选择“教师”登录。

#### 数据变化

```text
InstitutionMember(institution, user, teacher, active)
UserRole(user, teacher, active)
```

原有的 `UserRole(student)` 不应删除，因此该账号之后可以在学生和教师之间切换。

#### 安全边界

普通用户选择教师登录时仍应返回 `ROLE_NOT_GRANTED`。教师角色必须来源于机构管理员、平台管理员或其他受控业务授权。

### 17.3 转换二：家长账号转为教师账号

#### 当前支持情况

当前支持，操作方式与“学生转教师”相同。

#### 操作步骤

1. 机构管理员进入机构详情。
2. 使用家长账号绑定的同一手机号添加机构成员。
3. 选择“教师”并填写教师资料。
4. 添加成功后使用同一手机号选择教师登录。

#### 数据变化

```text
原有 UserRole(parent) 保留
新增 UserRole(teacher)
新增 InstitutionMember(role=teacher)
```

家长与学生的 `StudentParentBind` 关系也应保留，不因成为教师而自动解除家长关系。

### 17.4 转换三：教师账号转为家长账号

#### 当前支持情况

当前已支持。

#### 操作步骤

1. 教师使用原手机号完成短信验证。
2. 登录页主动选择“家长”。
3. 登录服务检查 `UserRole(parent)`。
4. 如果不存在 parent 记录，事务内自动创建。
5. 登录成功后进入家长端。

#### 数据变化

```text
原有 UserRole(teacher) 保留
新增 UserRole(parent, grant_source=self_login)
active_role=parent
```

自动开通 parent 只授予家长端资格，不会自动绑定任何学生。查看学生数据前，仍需完成家长绑定并经过学生确认。

### 17.5 转换四：教师账号转为学生账号

#### 当前支持情况

当前没有完整的页面操作链路。

现有学生加入班级接口要求当前会话已经是学生角色，而教师账号通常没有 `UserRole(student)`，因此教师直接选择学生登录可能返回 `ROLE_NOT_GRANTED`，形成首次转换障碍。

#### 推荐操作方式

新增受控的“添加班级学生”操作：

1. 教师或机构管理员进入班级学生管理。
2. 输入已有教师账号的手机号。
3. 确认将该账号加入指定班级。
4. 后端创建或恢复 `ClassStudent(status=active)`。
5. 由 `ClassStudent` 生效逻辑授予 `UserRole(student)`。
6. 账号重新登录学生端或直接使用角色切换进入学生端。

也可以由平台管理员在账号角色管理页面直接授予 student，但推荐优先通过班级关系授予，确保学生身份具备明确的业务归属。

#### 数据变化

```text
原有 UserRole(teacher) 保留
新增 ClassStudent(class, user, active)
新增 UserRole(student, active)
```

退出某个班级时，不应立即删除全局 student 角色，除非系统确认该账号已经不属于任何班级且产品明确要求自动回收学生角色。

### 17.6 转换五：家长账号转为学生账号

#### 当前支持情况

当前没有完整的页面操作链路，原因与教师转学生相同：家长会话不能直接调用要求学生会话的入班接口。

#### 推荐操作方式

1. 机构管理员或班级教师在班级学生管理中输入家长账号手机号。
2. 确认将该账号作为学生加入班级；必要时要求补充年级信息。
3. 后端创建或恢复 `ClassStudent(status=active)`。
4. 生效逻辑授予 `UserRole(student)`。
5. 家长账号可以通过角色切换进入学生端。

家长角色和已有 `StudentParentBind` 关系必须保留。一个人同时是自己孩子的家长和学生时，仍应禁止把自己的账号绑定为自己的孩子，避免产生自绑定关系。

### 17.7 四角色共存：admin、teacher、parent、student

#### 目标状态

一个账号可以同时拥有四条有效全局角色记录：

```text
UserRole(admin, active)
UserRole(teacher, active)
UserRole(parent, active)
UserRole(student, active)
```

`UserAccount.role_type` 只作为历史兼容字段，不应被反复修改为当前登录角色。

#### 推荐配置流程

| 角色 | 推荐授权方式 |
|---|---|
| `admin` | 平台管理员或受控管理命令授予，不允许普通登录自助获取 |
| `teacher` | 机构管理员添加为教师，或平台管理员授予 |
| `parent` | 验证身份后选择家长登录，或有效家长绑定关系授予 |
| `student` | 加入班级并创建 `ClassStudent`，或平台管理员直接授予 |

机构管理员 `InstitutionMember(role=admin)` 不等同于平台 `UserRole(admin)`，二者应分别管理和校验。

#### 登录和切换效果

登录任意一个已授权角色后，接口应返回全部 active 角色：

```json
{
  "roles": ["admin", "teacher", "parent", "student"],
  "active_role": "teacher"
}
```

用户可以通过 `/auth/switch-role` 在四种角色之间切换。切换时：

- 不重新输入短信验证码；
- 不清除其他角色；
- 不修改 `UserAccount.role_type`；
- 重新签发绑定新 `active_role` 的 Token；
- 按目标角色跳转对应端页面。

### 17.8 当前页面能力与缺口

| 功能 | 当前页面是否支持 | 说明 |
|---|---:|---|
| 学生/家长添加为教师 | 支持 | 机构详情添加成员，输入同一手机号 |
| 教师转家长 | 支持 | 选择家长登录自动开通 |
| 教师转学生 | 不完整 | 缺少已有账号加入班级并授予 student 的管理入口 |
| 家长转学生 | 不完整 | 缺少已有账号加入班级并授予 student 的管理入口 |
| 直接授予平台 admin | 不支持 | 当前主要通过受控命令或后台业务完成 |
| 四角色统一勾选管理 | 不支持 | 尚无全局账号角色管理页面 |
| 四角色登录后切换 | 后端和前端已支持 | 依赖四条 `UserRole` 均为 active |

### 17.9 推荐新增的管理能力

建议后续新增“账号角色管理”页面，但必须与机构成员管理分开：

1. 通过手机号查询唯一账号。
2. 展示账号当前全局角色、机构关系、班级关系、家长绑定关系。
3. 提供受权限控制的角色授予和撤销操作。
4. 授予 `teacher` 时可同步选择机构和教师资料。
5. 授予 `student` 时优先选择班级并创建 `ClassStudent`，而不是只写一条孤立角色记录。
6. 授予 `parent` 时只开通家长端权限，不自动创建孩子关系。
7. `admin` 只能由平台超级管理员操作，并记录审计日志。
8. 撤销角色前检查当前会话、机构关系、班级关系和家长绑定，避免造成数据访问断裂。

### 17.10 验收标准

1. 学生账号被机构添加为教师后，可以登录教师端，并仍可切回学生端。
2. 家长账号被机构添加为教师后，可以登录教师端，并仍可切回家长端。
3. 教师选择家长登录时自动创建 parent，原 teacher 不丢失。
4. 教师被加入班级后获得 student，并可在教师、学生之间切换。
5. 家长被加入班级后获得 student，原 parent 和家长绑定关系不丢失。
6. 四角色账号登录后返回四个不重复角色，并可以连续切换四种角色。
7. 普通用户不能仅通过登录页选择 teacher 或 admin 自助获得权限。
8. 角色撤销、账号停用后，旧 Token、角色切换和对应业务接口均按权限规则失效。
