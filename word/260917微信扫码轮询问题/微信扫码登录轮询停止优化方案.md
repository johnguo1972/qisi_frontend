# 微信扫码登录轮询停止优化方案

## 1. 文档信息

- 编制日期：2026-09-17
- 适用范围：H5 微信扫码登录、短信验证码登录、退出登录、Token 过期后的登录流程
- 当前状态：优化方案，暂不修改代码
- 目标：避免用户已经登录或离开微信登录页面后，`/api/v1/auth/wechat-device/status` 仍持续请求，同时保证微信扫码登录功能正常使用

## 2. 问题描述

H5 登录页面默认使用微信登录。页面挂载后会自动创建微信设备登录会话，并立即查询一次状态；如果状态仍为待处理，则每 3 秒调用一次：

```text
GET /api/v1/auth/wechat-device/status?web_session_id=...
```

当前页面在销毁时虽然会清理定时器，但轮询启动和异步请求之间缺少统一的页面状态、登录方式和 Token 校验，存在以下问题：

1. 用户切换到短信登录后，之前已经发起的微信会话创建请求可能仍在执行。
2. 微信会话创建请求返回时，没有再次确认页面是否仍处于微信登录模式，可能重新启动轮询。
3. 短信登录成功后，正常情况下页面会销毁并停止轮询，但如果存在异步竞态、页面未真正销毁或其他登录页标签，轮询仍可能继续。
4. 轮询请求没有防并发控制，接口响应时间超过 3 秒时，可能出现多个状态请求同时执行。
5. 当前轮询逻辑不主动检查用户是否已经存在有效 Token，不能仅依赖登录页销毁来停止请求。

## 3. 当前代码调用链路

### 3.1 前端接口封装

文件：`uniapp/src/api/wechat-device.ts`

```ts
wechatDeviceApi.status(webSessionId)
```

该方法请求 `/auth/wechat-device/status`，由 `request.ts` 拼接成完整 API 地址。

### 3.2 前端实际轮询位置

文件：`uniapp/src/pages/login/index.vue`

- `pollWechatDeviceStatus()` 调用状态接口。
- `createWechatDeviceSession()` 创建会话后立即查询一次状态。
- 状态仍未完成时，通过 `setInterval(..., 3000)` 每 3 秒再次查询。
- `onUnmounted()` 中调用 `stopWechatDevicePolling()` 清理定时器。

### 3.3 后端接口位置

- 路由：`apps/accounts/urls.py` 中的 `wechat-device/status`
- 处理函数：`apps/accounts/views.py` 中的 `wechat_device_status`

后端接口的职责是读取并返回微信设备登录状态，不会主动创建定时器，也不会主动调用浏览器。持续请求的根源在前端登录页面轮询逻辑。

## 4. 优化目标

### 4.1 必须满足的行为

| 场景 | 预期行为 |
| --- | --- |
| 未登录，进入 H5 登录页，默认微信登录 | 创建二维码并启动轮询 |
| 未登录，用户选择微信登录 | 创建二维码并启动轮询 |
| 微信二维码处于待扫码、待确认状态 | 继续轮询 |
| 微信扫码并确认成功 | 停止轮询，完成登录并跳转 |
| 用户切换到短信登录 | 立即停止轮询并清空微信会话状态 |
| 短信验证码登录成功 | 停止轮询并跳转业务页面 |
| 用户已经存在有效 Token | 不启动微信轮询 |
| 用户退出登录 | 停止当前轮询，跳转登录页 |
| Token 过期并回到登录页 | 只有选择微信登录时才重新启动轮询 |
| 二维码会话过期 | 停止旧轮询，重新生成一个会话并启动一个新的轮询 |
| 页面离开、隐藏或销毁 | 停止轮询并使未完成的异步流程失效 |

### 4.2 非目标

本方案不改变以下业务内容：

- 微信二维码生成接口及二维码内容；
- 微信小程序扫码、手机号授权、登录确认流程；
- 微信登录完成接口及 Token 生成逻辑；
- 短信验证码发送、校验及登录结果；
- 后端登录状态的数据结构和接口返回含义。

## 5. 具体修复方案

### 5.1 建立统一的轮询运行条件

轮询启动和每次请求前都应统一检查以下条件：

1. 当前页面实例仍然有效；
2. 当前页面仍处于登录页；
3. 当前登录方式仍为微信登录；
4. 用户没有有效的 `accessToken`；
5. 当前微信设备会话仍是本页面最新创建的会话；
6. 当前没有正在完成微信登录的流程。

只要任一条件不满足，就不应启动新的轮询，并应清理已有定时器。

不能只在 `onUnmounted()` 中清理，也不能只依赖后端接口返回错误。因为页面可能暂时隐藏、登录方式可能已切换，或者异步请求可能在页面销毁后才返回。

### 5.2 短信登录时立即停止微信轮询

用户切换到短信登录时，应执行以下操作：

1. 清理微信轮询定时器；
2. 使当前微信会话失效，避免旧请求返回后继续使用；
3. 标记当前登录方式为手机号；
4. 不再创建微信二维码或启动微信状态查询。

短信登录成功时，在保存 Token 和跳转前再次执行停止轮询，形成显式兜底。这样即使页面跳转存在延迟，也不会继续发起微信状态请求。

### 5.3 微信登录成功时停止轮询

微信状态返回有效登录凭证后，应按照以下顺序处理：

1. 立即清理轮询定时器；
2. 标记为“正在完成登录”，阻止后续状态查询；
3. 调用微信登录完成接口；
4. 保存 Token 和用户信息；
5. 跳转到对应业务页面。

如果完成接口失败，应根据业务需要允许用户重新生成二维码，但必须先清理旧轮询状态，不能同时保留多个轮询定时器。

### 5.4 处理异步请求返回后的竞态

这是本次优化的重点。

`createWechatDeviceSession()` 是异步函数。页面加载后可能已经发起创建微信会话请求，此时用户切换到短信登录或已经登录成功，创建请求才返回。返回后不能无条件设置 `setInterval`。

建议为每次微信会话或页面生命周期增加递增版本号/请求序号：

```text
开始创建会话：记录当前 requestVersion
切换登录方式、登录成功、退出页面：requestVersion 递增
异步请求返回：只有返回时的 requestVersion 仍是最新值，才允许设置轮询
```

异步请求返回后至少再次确认：

- 页面没有销毁；
- 登录方式仍是微信；
- 当前没有有效 Token；
- 本次会话仍是最新会话；
- 没有正在完成其他登录。

否则直接丢弃返回结果，不设置新的定时器。

### 5.5 防止轮询请求重叠

当前使用固定 `setInterval`。如果某次接口请求超过 3 秒，下一次定时器可能在上一次请求结束前再次执行。

建议使用“单次请求完成后再调度下一次”的方式，或者增加 `pollingInFlight` 标志：

```text
请求开始：标记 pollingInFlight = true
请求未结束：后续触发直接跳过
请求结束：标记 pollingInFlight = false
仍满足轮询条件：安排下一次查询
不满足条件：停止调度
```

这样可以保证同一页面、同一会话最多只有一个状态请求在执行。

### 5.6 页面生命周期和浏览器可见性处理

除了 `onUnmounted()`，建议补充页面隐藏和浏览器标签页不可见处理：

- 页面 `onHide` 或 `onUnload` 时停止轮询；
- H5 `document.visibilityState === 'hidden'` 时暂停轮询；
- 页面重新可见时，仅当用户未登录且仍选择微信登录时恢复轮询；
- 恢复时复用当前有效会话，只有会话过期才重新创建二维码。

这样可以减少用户切换标签页、最小化浏览器或暂时离开页面时的无效请求。

### 5.7 Token 过期和退出登录处理

退出登录时应统一执行：

1. 清理微信轮询；
2. 清理微信设备会话和请求版本状态；
3. 清理 Token 和用户信息；
4. 跳转到登录页。

Token 过期后，登录页可以恢复默认微信登录，但必须先确认旧页面轮询已经停止，避免旧会话和新会话同时查询。

需要注意：状态接口允许未登录访问，因此 `request.ts` 是否携带 Token 不能作为停止轮询的依据，必须由登录页面主动判断登录状态。

## 6. 对微信扫码登录功能的影响评估

按本方案修复不会改变正常微信扫码登录流程：

1. 未登录并选择微信登录时，仍然会创建二维码；
2. 待扫码和待确认状态仍然会持续查询；
3. 扫码确认成功后仍然会调用登录完成接口；
4. 登录成功后仅停止不再需要的状态查询；
5. 二维码过期时仍然可以重新生成并继续登录；
6. 用户切换到短信登录后，不会再被微信轮询干扰。

修复的影响范围仅限于“何时启动和停止轮询”，不应修改微信登录接口、状态值、Ticket 处理和 Token 保存逻辑。

## 7. 资源收益

当前单个登录页在待扫码期间每 3 秒请求一次，约每分钟 20 次请求。单次请求开销通常不大，但长期运行、多个标签页同时打开或请求重叠时，会产生不必要的：

- 浏览器定时器和网络请求；
- 后端接口处理、日志记录和状态查询；
- 数据库、缓存或会话存储访问；
- 请求对象和回调对象的临时内存占用。

修复后，已登录、已切换手机号、页面隐藏或页面销毁时不再产生轮询请求，并通过单请求锁避免请求重叠。该方案可以消除无效请求和潜在的定时器残留，降低通道和内存资源浪费。

## 8. 验证方案

### 8.1 功能验证

1. 清理浏览器 Token，打开 H5 登录页，确认默认微信登录能够生成二维码。
2. 确认待扫码期间状态接口约每 3 秒调用一次。
3. 使用微信扫码并确认，确认状态接口停止，登录完成接口调用一次，能够正常进入业务页面。
4. 打开微信登录后切换到短信登录，确认状态接口立即停止。
5. 使用短信验证码登录成功，确认跳转后不再出现微信状态请求。
6. 已登录状态刷新页面，确认不会创建新的微信轮询。
7. 退出登录后选择微信登录，确认能够重新生成二维码并开始轮询。
8. 模拟 Token 过期，确认回到登录页后只有在微信登录模式下才轮询。
9. 等待二维码过期，确认旧定时器被清理，重新生成后只有一个新的轮询。

### 8.2 生命周期验证

1. 微信登录页切换到其他页面，确认状态请求停止。
2. H5 标签页切换到后台，确认轮询暂停。
3. 标签页恢复前台，确认仅在未登录且微信模式下恢复。
4. 登录页快速切换“微信登录/短信登录”多次，确认不会出现多个定时器。
5. 在微信会话创建请求尚未返回时完成短信登录，确认请求返回后不会重新启动轮询。
6. 同时打开多个标签页，确认每个页面只维护自己的会话，关闭登录页后不再继续请求。

### 8.3 请求验证

在浏览器开发者工具 Network 面板检查：

- 短信登录成功后没有新的 `/wechat-device/status` 请求；
- 微信登录成功后没有新的 `/wechat-device/status` 请求；
- 同一时间最多只有一个状态请求处于 Pending；
- 没有同一页面同时运行多个 3 秒轮询定时器；
- 请求的 `web_session_id` 不会在旧会话失效后继续长期使用。

## 9. 验收标准

满足以下条件，才认为本次优化完成：

- 微信扫码登录可以正常完成；
- 短信登录可以正常完成；
- 微信登录成功后状态接口停止调用；
- 短信登录成功后状态接口停止调用；
- 已登录刷新页面不会自动启动微信轮询；
- 退出登录后重新选择微信登录可以重新轮询；
- 页面隐藏、离开或销毁后不会残留轮询；
- 快速切换登录方式不会产生旧异步请求重新启动定时器；
- 不存在重复定时器和重叠状态请求；
- 后端微信登录相关接口的业务结果未发生变化。

## 10. 实施注意事项

1. 本方案只调整前端轮询的启动、停止和生命周期控制，不修改后端接口协议。
2. 所有停止入口应复用统一的清理函数，避免在多个位置重复编写清理逻辑。
3. 定时器、请求锁、页面有效标记和会话版本号应保持职责清晰，避免引入重复状态。
4. 不能通过简单删除轮询或固定延时停止的方式处理，否则会影响用户正常扫码登录。
5. 修改完成后必须执行功能验证、生命周期验证和 Network 请求验证。

## 11. 结论

当前问题的根因是 H5 登录页自动启动微信扫码状态轮询，而轮询停止条件不完整，尤其缺少对 Token、登录方式、页面生命周期和异步竞态的统一控制。

按本方案实施后，只有“未登录且处于微信登录模式”的页面才会轮询；用户完成短信登录、微信扫码登录、退出登录、离开页面或页面隐藏后，轮询都会停止。只要保留原有微信登录成功处理链路，并按验收标准验证，不会影响微信扫码登录和短信登录的正常功能。
