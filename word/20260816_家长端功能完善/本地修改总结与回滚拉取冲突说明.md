## 一、文档目标

本文用于统一后续家长端功能完善的业务口径和技术实施范围，目标是：

1. 解决学生账号选择家长角色登录时返回 `ROLE_NOT_GRANTED` 的问题。
2. 建立明确的家长角色授权和家长-学生绑定流程。
3. 让家长可以安全查看一个或多个孩子的学习数据。
4. 让学生端的学习行为能够在家长端形成可追踪、可解释的反馈闭环。
5. 兼容 H5、APP、微信小程序，不改变教师端和管理员端现有业务。
6. 保留学生端原有登录、班级、任务、答题、错题和成长流程。

本文重点是“当前实际代码”和“后续闭环方案”。之前的回滚说明仅作为历史参考，不能直接视为当前代码状态。

## 三、当前角色和账号权限模型

### 3.1 账号表

账号模型：

```text
apps/accounts/models.py -> UserAccount
数据库表：user_account
```

主要字段：

- `id`：用户唯一标识；
- `mobile`：手机号，当前唯一；
- `role_type`：历史兼容字段，不能单独作为多角色授权依据；
- `status`：账号状态；
- `display_name`、`grade_level` 等资料字段。

### 3.2 角色授权表

角色模型：

```text
apps/accounts/models.py -> UserRole
数据库表：user_role
```

有效角色由以下条件决定：

```text
user = 当前账号
role = 目标角色
status = active
```

可用角色：

```text
admin
teacher
parent
student
```

登录流程不会因为前端选择了某个角色就自动授权。登录时会检查：

```text
has_user_role(user, active_role)
```

不存在有效授权时返回：

```text
ROLE_NOT_GRANTED
Role is not granted
```

### 3.3 当前会话角色

用户可以有多个有效角色，但一个 JWT 会话只有一个：

```text
active_role
```

例如：

```json
{
  "roles": ["admin", "teacher", "parent", "student"],
  "active_role": "parent"
}
```

此时请求按照家长身份校验，不能因为 `roles` 中存在 `student` 就直接访问所有学生接口。

### 3.4 测试账号的特殊情况

当服务器配置以下固定测试登录信息时：

```env
TEST_LOGIN_ENABLED=1
TEST_LOGIN_PHONE=15800010001
TEST_LOGIN_CODE=651234
```

代码会调用 `ensure_fixed_test_account()`，为这个特定账号授予四种角色。

这只对手机号和验证码同时匹配的测试账号生效。普通学生账号不会因为界面上显示了“家长”选项，就自动获得 `parent` 角色。

## 四、当前问题的准确原因

用户在登录页选择家长端时，前端会提交：

```json
{
  "mobile": "用户手机号",
  "verify_code": "验证码",
  "role_type": "parent"
}
```

后端处理链路为：

```text
选择家长角色
    -> active_role = parent
    -> 查询 UserRole(parent)
    -> 当前账号没有有效 parent 授权
    -> 返回 HTTP 403
```

所以截图中的错误不是页面路由问题，也不是验证码问题，而是账号授权缺失。

需要特别区分：

```text
前端显示角色按钮 ≠ 账号已获得该角色
UserAccount.role_type = student ≠ UserRole(parent)
拥有 student 角色 ≠ 自动拥有 parent 角色
```

## 五、当前家长-学生关系模型

绑定模型：

```text
apps/accounts/models.py -> StudentParentBind
数据库表：student_parent_bind
```

主要字段：

- `student_user_id`：学生账号；
- `parent_user_id`：家长账号；
- `relation_type`：父亲、母亲、监护人等；
- `bind_status`：`pending`、`active` 等状态；
- `bound_at`：绑定时间。

只有以下关系才可以用于家长查看数据：

```text
bind_status = active
```

当前已实现的家长接口：

```text
GET  /api/v1/parent/children
POST /api/v1/parent/context
```

接口作用：

- `/parent/children`：查询当前家长已有的有效孩子；
- `/parent/context`：在已绑定孩子中选择当前查看对象。

这两个接口都不会创建绑定关系。

当前前端的 `/pages/student/parent-bind` 是微信账号绑定手机号页面，不是家长绑定学生页面。

## 七、目标业务闭环

本项目正式采用“学生账号 + 家长账号”两个账号的绑定模式。学生和家长使用不同手机号，对应两个独立的 `UserAccount`，通过 `StudentParentBind` 建立关系。

目标闭环如下：

```text
学生账号登录
    -> 学生生成申请码/二维码
    -> 家长输入手机号和验证码
    -> 家长自动登录或注册家长账号
    -> 家长输入申请码
    -> 创建 pending 家长-学生绑定申请
    -> 学生端查看待确认申请
    -> 学生确认或拒绝
    -> 确认后绑定状态变为 active
    -> 确保家长拥有 parent 角色、学生拥有 student 角色
    -> 查询孩子列表
    -> 选择孩子并建立 parent_context
    -> 家长只读查看孩子学习数据
    -> 学生完成任务和答题
    -> 学习数据写入学生账号
    -> 家长端重新查询并展示最新进度
    -> 家长可继续绑定其他学生并切换查看
```

### 7.1 正式绑定流程

不建议只使用学生手机号直接绑定，因为手机号容易被误填或被越权使用。建议采用学生端生成绑定码或二维码的方式。

正式流程：

1. 学生端进入“家长绑定”。
2. 学生生成一次性申请码或二维码，申请码明确对应当前学生。
3. 家长输入手机号并获取验证码。
4. 验证成功后，家长自动登录；新手机号创建家长账号，已有家长账号继续使用。
5. 家长进入“添加孩子”，输入或扫描学生申请码。
6. 后端校验申请码有效期、使用次数和目标学生。
7. 后端创建 `StudentParentBind`，状态为 `pending`。
8. 家长可以继续提交其他学生的申请码，形成多个待确认关系。
9. 学生端显示待确认申请，只允许对应学生本人确认或拒绝。
10. 学生确认后，绑定状态变为 `active`；拒绝后状态变为 `rejected`。
11. `active` 关系确保家长拥有 `parent` 角色，学生拥有 `student` 角色。
12. 家长刷新 `/parent/children`，选择孩子并调用 `/parent/context`。
13. 家长只能查看状态为 `active` 且属于自己的孩子。

### 7.2 两账号和多孩子规则

- 学生和家长是两个独立账号，手机号不同；
- 一个家长可以绑定多个学生；
- 一个学生可以绑定多个家长；
- 同一对家长和学生不能重复创建有效绑定；
- 家长只有在学生确认后才能查看数据；
- 家长解除一个孩子关系时，不影响其他孩子关系；
- 当前孩子上下文必须从家长自己的有效绑定关系中选择；
- 本项目不以“同一个账号自关联”作为正式业务模式。

家长账号可以拥有其他业务角色，但本绑定流程不自动把一个已有学生账号改成家长账号。已有学生账号如果要成为家长账号，必须经过单独的角色授权流程，不能依靠登录页选择角色静默开通。

## 八、后端功能完善清单

### 8.1 角色授权

需要完善：

- 普通账号首次登录默认授予学生角色；
- 教师由机构成员管理授予教师角色；
- 平台管理员由平台管理流程授予管理员角色；
- 家长在有效绑定关系建立后授予家长角色；
- 登录接口只校验授权，不在登录时偷偷改写角色；
- 角色撤销后已有 JWT 不能继续使用已撤销角色；
- 返回清晰的角色未授权错误码。

保持不变：

- 教师端权限；
- 管理员端权限；
- 学生班级加入和退出逻辑；
- 学生任务、答题、错题和成长数据写入逻辑。

### 8.2 家长绑定接口

本次实现的绑定业务接口如下：

```text
POST /api/v1/student/parent-bind-codes
POST /api/v1/parent/bind-requests
GET  /api/v1/parent/bind-requests/pending
GET  /api/v1/student/parent-bind-requests
POST /api/v1/student/parent-bind-requests/{id}/decision
DELETE /api/v1/parent/binds/{id}
GET  /api/v1/parent/children
POST /api/v1/parent/context
```

接口必须校验：

- 当前账号身份；
- 家长手机号验证码登录或注册状态；
- 绑定码或二维码有效性；
- 绑定码是否过期；
- 绑定码是否已经使用；
- 学生和家长账号状态；
- 只有对应学生本人可以确认或拒绝申请；
- 是否已经存在有效绑定；
- 是否超过绑定数量限制；
- 解除绑定后的数据访问权限；
- 当前孩子上下文是否仍然有效。

当前实现中，学生确认接口使用统一的 `decision` 请求参数：

```json
{ "decision": "approve" }
```

拒绝时传入 `reject`。绑定码由服务端缓存保存 600 秒，提交成功后立即失效，不新增数据库表或字段。

### 8.3 家长数据访问

建议保留以下原则：

1. `/student/my-classes` 继续是学生专用接口。
2. 家长不直接伪装成学生调用班级管理接口。
3. 家长查看孩子学习数据必须经过 `StudentParentBind` 校验。
4. 所有家长代理接口统一获得 `effective_student_user`。
5. 查询任务、进度、错题、成长和知识掌握时都使用有效孩子 ID。
6. 不允许家长通过请求参数直接传入任意学生 ID越权查询。
7. 家长解除绑定后立即失去对应孩子的数据访问权限。

### 8.4 家长数据接口规划

建议将家长数据接口分为两类：

#### 家长关系接口

```text
/parent/children
/parent/context
/parent/bind-requests
/parent/binds
```

#### 家长只读学习接口

可以复用已有学生业务查询逻辑，但必须统一经过家长上下文校验；也可以逐步增加明确的 `/parent/*` 只读接口：

```text
/parent/overview
/parent/missions
/parent/missions/{id}
/parent/wrong-book
/parent/growth
/parent/knowledge-mastery
/parent/reports
```

优先保证查询口径一致，再决定是否保留学生接口复用方式。

### 9.5 错误提示

前端公共请求层应统一解析：

```text
detail
message
error
```

```text
后端 detail/message/error
    -> 业务默认提示
    -> HTTP 状态码提示
```

典型提示建议：

| 场景 | 用户提示 |
|---|---|
| 未授权家长角色 | 当前账号尚未开通家长角色 |

| 未选择孩子 | 请先选择要查看的孩子 |
| 绑定已失效 | 当前绑定已失效，请重新绑定 |
| 学生没有班级 | 当前学生尚未加入班级 |
| 网络故障 | 网络请求失败，请稍后重试 |

## 十八、方案复核补充：执行前必须解决的关键问题

上一轮复核发现，前文已经覆盖总体方向，但以下内容如果不明确，直接按方案执行仍可能无法形成真正闭环。本节作为实施前的强制约束，优先级高于一般页面开发。

### 18.1 首次家长角色开通存在先后矛盾

当前登录流程是：

```text
选择 parent
  -> 检查 UserRole(parent)
  -> 没有授权
  -> 返回 ROLE_NOT_GRANTED
```

而当前角色授予信号是：

```text
StudentParentBind 保存为 active
  -> 授予 parent 和 student 角色
```

如果绑定功能只允许 `active_role=parent` 的用户访问，就会出现：

```text
没有 parent 角色，无法登录家长端
无法登录家长端，无法完成首次绑定
没有绑定关系，又不会自动获得 parent 角色
```

实施时必须选择并实现以下一种启动方式：

#### 正式方案：两个账号绑定

本项目不采用“已有学生账号选择 parent 后自动变成家长”的方式，也不采用同一账号自关联作为正式业务。

正式流程固定为：

```text
学生账号登录
  -> 生成学生申请码
  -> 家长手机号获取验证码
  -> 家长自动登录或注册独立家长账号
  -> 家长输入学生申请码
  -> 创建 pending 绑定申请
  -> 学生端确认或拒绝
  -> 确认后变为 active
  -> 家长选择孩子并查看数据
```

首次家长登录必须允许新手机号创建家长账号并进入家长端；但在绑定关系变为 `active` 前，家长只能看到绑定引导，不能查看任何学生数据。

已有学生账号选择家长角色时，如果该账号没有 `UserRole(parent)`，仍应返回明确的未授权提示，不能自动改变账号身份。

### 18.2 手机号和多孩子规则

当前 `UserAccount.mobile` 是唯一字段，因此正式方案要求：

- 家长账号和学生账号使用不同手机号；
- 一个家长账号可以对应多个学生账号；
- 一个学生账号可以对应多个家长账号；
- 同一对账号不能重复创建有效绑定；
- 业务关系以 `StudentParentBind` 为准，不以手机号相同作为绑定依据；
- 如果未来必须支持同手机号多身份，需要另行设计身份映射模型和数据库迁移，不能在本方案中直接绕过唯一约束。

### 18.3 绑定码必须有完整安全规则

绑定码或二维码不能只是前端传入学生 ID。至少需要明确：

- 由学生端生成；
- 随机且不可预测；
- 有效期；
- 是否一次性使用；
- 是否限制使用次数；
- 是否绑定目标学生；
- 绑定成功后立即失效；
- 无效、过期、重复使用时的错误码；
- 是否记录生成者、使用者和时间；
- 不能通过手机号遍历学生账号。

如果绑定码、申请状态和审核日志需要持久化，就必须新增模型和 migration；如果使用缓存一次性令牌，则必须接受缓存丢失后需要重新生成、审计信息较少等限制。

### 18.4 绑定解除和角色撤销必须有规则

当前信号只负责授予角色，不负责撤销角色。后续必须定义：

1. 解除一个孩子关系时，不能误撤销仍绑定其他孩子的家长角色。
2. 所有有效孩子关系解除后，是否撤销 `parent` 角色。
3. 学生角色不能因为解除家长关系被误撤销。
4. 解除绑定后立即清理 `parent_context` 和前端 `activeChildId`。
5. 已有 token 在角色撤销后必须重新进行角色校验。
6. 解除绑定后，历史学习记录是否保留只读快照，需要明确业务规则。

### 18.5 学生数据接口必须逐项验证代理对象

不能只验证 `/student/home`。以下接口需要逐项确认家长访问时使用的是当前绑定孩子，而不是家长自身：

```text
任务首页
任务详情
关卡详情
错题本
同类题
成长
知识掌握
引导式解题
答题记录
导出数据
```

每个接口都需要满足：

```text
家长角色
  -> 有效绑定关系
  -> 已选择当前孩子
  -> 统一取得 effective_student_user
  -> 只读查询孩子数据
```

不能仅依赖修改 `request._user` 的隐式行为；关键查询应明确使用有效学生对象，并增加家长代理场景测试。

### 18.6 家长端页面范围必须区分“已实现”和“规划中”

当前家长端不能按完整家长平台描述验收。目前已经具备的范围主要是：

```text
家长独立入口
已绑定孩子查询
当前孩子选择
孩子任务概览
```

以下功能仍属于规划或待实现：

```text

绑定确认/审核
解除绑定
错题页面
成长分析页面
知识掌握页面

学习报告

```

后续不能只增加菜单文字，必须同时实现对应 API、权限校验、空状态和多端页面。

### 18.7 小程序全局 tabBar 不能直接复用学生菜单

当前 `pages.json` 的全局 tabBar 是学生端菜单。家长端如果直接复用，会再次出现家长身份进入学生菜单的问题。

实施时必须选择：

- 使用家长自定义导航/抽屉；或
- 设计按角色切换的导航壳；或
- 使用独立家长小程序页面结构。

家长端不能只新增路由而不处理全局学生 tabBar。

### 18.8 测试数据必须覆盖完整闭环

仅有四角色测试账号不能证明家长功能完整。完整测试至少需要：

- 一个拥有 student 角色的账号；
- 一个拥有 parent 角色的账号，或同账号多角色模式；
- 一条 `StudentParentBind(active)`；
- 至少一个有效 `ClassStudent`；
- 至少一个已发布任务；
- 至少一条任务进度或答题记录；
- 多孩子场景一组；
- 解除绑定场景一组。

`15800010001` 只能验证四角色登录和切换。没有 `StudentParentBind` 时，家长端显示无孩子是正常结果，不代表绑定功能已经完成。

## 十九、文档复核后的最终执行结论

本方案经过复核后，结论如下：

```text
只修复前端家长路由       -> 不能解决 ROLE_NOT_GRANTED
只增加 parent 角色       -> 不能解决家长查看哪个学生的问题
只增加 StudentParentBind -> 还需要首次授权入口和上下文设置
只增加家长页面           -> 不能保证后端数据不越权
```

只有同时完成以下链路，才能认为功能闭环：

```text
首次身份开通
  -> parent 角色授权
  -> 安全绑定码
  -> StudentParentBind(active)
  -> 家长孩子列表
  -> 当前孩子上下文
  -> 统一代理学生对象
  -> 家长只读学习数据
  -> 学生学习数据持续更新
  -> 解除绑定和权限撤销
```

因此，当前代码已经完成“两个账号绑定、多孩子、学生确认”的核心开发链路：家长可以通过手机号验证码自动注册/登录，学生生成申请码，家长提交待确认申请，学生确认后建立有效关系，家长再选择和切换孩子。家长学习报告、趋势分析、通知提醒等扩展页面仍需后续开发，不能将这些未完成的扩展功能误认为已经交付。
